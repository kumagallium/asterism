# つながったデータの基礎 — RDF・オントロジー・SPARQL

Asterism は、表を「つながったデータ」に変える道具です。この章では、その裏
側にある考え方を、はじめての人向けに説明します。操作はありません。読むだ
けの章です。

## 表のままだと何が困るか

料理のレシピを書きためた表です。

```
作成者: 山田                          ← 表の外（ファイルの先頭に書かれている）
作成日: 2026-09-01
出典: 家庭料理の記録
----------------
料理名,食材名,分量,単位              ← ここから下が表
カレー,にんじん,2,本
カレー,じゃがいも,3,個
肉じゃが,にんじん,1,本
```

人が見ればわかりますが、機械にとっては文字が並んだ格子です。この形だけからは、
次のことがわかりません。

- `分量` の `2` が何の 2 なのか（本数なのか、人前なのか）
- 1 行目と 3 行目の「にんじん」が、**同じにんじんのこと**なのか
- 隣の人が作った価格表の「にんじん」と、この「にんじん」は同じものなのか

**つながったデータ**とは、この「わからないこと」を機械が読める形で明記した
データのことです。人が毎回説明しなくても、機械が正しく解釈できます。

## 事実は 3 つ組で書く

つながったデータでは、すべてを「**なにが** — **どんな項目で** — **どんな
値か**」という 3 つ組で書きます。この 3 つ組ひとつが、**事実 1 件**です。
標準の用語では**トリプル**（triple）と呼びます。

上の表の 1 行目は、こう書き換わります。主語の名前に料理名が入っていることに
注目してください（理由は次の節）。

```
カレーのにんじん  ──[ 分量 ]──▶  2
カレーのにんじん  ──[ 単位 ]──▶  本
カレーのにんじん  ──[ 食材 ]──▶  にんじん
```

1 行 3 列だった表が、事実 3 件になりました。Asterism の画面が「事実 33 件」の
ように数えているのは、この 3 つ組の数です（11 行 × 3 項目 = 33）。

![表の 1 行が、主語ひとつと 3 つの述語・値の組に展開される図](../figures/triple.svg)

*1 行が事実 3 件になる。主語は 1 つ、述語（項目）が 3 つ、目的語（値）が 3 つ。*

3 つ組の各部分には名前があります。

| 位置 | 標準の用語 | 意味 | 上の例 |
|---|---|---|---|
| 1 番目 | 主語（subject） | 何についての事実か | カレーのにんじん |
| 2 番目 | 述語（predicate） | どの項目の話か | 分量 |
| 3 番目 | 目的語（object） | その値 | 2 |

**RDF** とは、この「事実は 3 つ組で書く」という決まりごとの名前です。特別
なソフトではなく、書き方の約束です。

## IRI — 世界でひとつの名前

3 つ組の主語と述語は、ただの文字列ではいけません。「にんじん」という名前は、
世界のあちこちの表に出てくるからです。そこで**世界でひとつに決まる名前**を
使います。これが **IRI** です。見た目は URL とそっくりです。

![IRI を、データの所在を表す部分・集まりを表す部分・1 件を指す部分に分解した図](../figures/iri.svg)

*IRI が同じなら同じもの、違えば違うもの。この一点だけで、別々の場所で作られた
データがあとから機械的につながる。*

IRI は 2 種類あります。

| 種類 | 何につける名前 | 例 |
|---|---|---|
| 実体（データ）の IRI | 実際のもの 1 件ずつ | `.../resource/使用量/カレー/にんじん` |
| 語彙（項目）の IRI | 項目や種類そのもの | `.../ontology#分量` |

Asterism が「ID のつけかた」を必ず人に確認するのは、この 1 件を指す部分をどの列
から組み立てるかを決めるためです。ここを間違えると、別々のものが同じ名前になって
しまい、あとから直すのが大変になります。

長い IRI を毎回書くのは大変なので、先頭部分に短い別名（**接頭辞**、prefix）を
付けて `recipe:分量` のように略記します。ファイルの先頭に並ぶ `prefixes:` は、
この対応表です。

## ID が衝突しないとはどういうことか

ここが設計でいちばん間違えやすいところなので、実例で説明します。上の使用量の
ID は、こう組み立てられています。

```
recipe:使用量/{料理名}/{食材名}
                │        └─ その行の食材
                └────────── その行の料理
```

もし `食材名` だけで名前を作ると、こうなります。

| 行 | 料理 | 食材 | 食材名だけの ID | 料理名も使った ID |
|---|---|---|---|---|
| 1 | カレー | にんじん | `使用量/にんじん` | `使用量/カレー/にんじん` |
| 4 | 肉じゃが | にんじん | `使用量/にんじん` ← **同じ** | `使用量/肉じゃが/にんじん` |

**食材名だけだと、カレーのにんじん（2 本）と肉じゃがのにんじん（1 本）が
同じ 1 件に潰れます。**あとから取り込んだ方が前の分量を上書きしてしまいます。

![食材名だけだと 1 件に潰れるが、料理名と組み合わせると別々の ID になることを示す図](../figures/id-collision.svg)

*ID の一意性は「どの範囲で一意か」で決まる。`食材名` はこの表の中で何度も出て
くるので、それだけでは名前にならない。*

**表の外の値も ID に使えます。** このファイルの先頭にある `作成者: 山田` は
表の列ではありませんが、取り込みのとき表の全行に配られるので、ID の材料にできます
（「読み取りの確認」で表の外の行の扱いを聞かれるのは、これを決めるためです）。
別の人が作った同じ形のレシピ表と混ざらないようにしたいなら、作成者を ID に
加えます。

これを人が確かめる場所が、かんたんモードの「できた形をたしかめる」の画面にある
②「ID がひとつずつを指しているか確かめる」です。ID が重ならないか（✓ / ⚠）
が表示され、⚠ が出たら組み合わせを選び直せます。

**ID が重ならないことと、つながっていることは別です。** 上の ID には料理名が
文字として入っていますが、これは「料理という別のもの」への参照ではありません。
「カレーに使う食材を全部」のような質問に答えられるようにするには、料理そのもの
をデータの種類として設計に足し、使用量からそこへの参照を持たせる必要があります
（次の節）。

## クラスと属性

事実をたくさん集めると、同じ形のものが繰り返し現れます。

- 使用量は、どれも料理・食材・分量・単位を持つ
- 食材は、どれも名前を持ち、店ごとの価格を持つ

この「使用量」「食材」という**種類**が**クラス**（class）です。そして、その
種類が持つ**項目**が**属性**（プロパティ）です。3 つ組の述語に来るのが属性だと
考えてください。

```
クラス「使用量」
 ├ 属性 分量        （値は数値）
 ├ 属性 単位        （値は文字）
 ├──▶ 料理         （別のものへの参照）
 └──▶ 食材         （別のものへの参照）

クラス「食材」
 └ 属性 名前        （値は文字）
```

属性の値には 2 種類あり、この違いが「つながる／つながらない」を決めます。

| 値の種類 | 中身 | 例 | できること |
|---|---|---|---|
| 値そのもの | 数値・文字・日付 | 分量 = `2` | 大小をくらべる、絞り込む |
| 別のものへの参照 | 相手の IRI | この使用量 → にんじん | またいでたどる |

後者があるから、データは網目状につながります。「にんじんを使う料理を全部」の
ような質問に答えられるのは、参照でつながっているときだけです。Asterism が
「つながっていません」と指摘するのは、この参照が無い状態のことです。

![「中身」タブ。このデータセットが持つ種類と、気になる点](../screenshots/dataset-structure.png)

*このデータセットには 2 種類があり、「気になる点」に「使われていない列があります」
と出ています。取り込まれていない列は、質問にも出てきません。*

## オントロジー — 共通の言葉

クラスと属性を決めて、名前（IRI）を与え、「このクラスはこの属性を持つ」
「この属性の値は数値」といった決まりを書いたもの。それが**オントロジー**
です。データそのものではなく、**データを書くための語彙集**だと考えるのが
いちばん近いです。

Asterism の画面では、これを**共通の言葉**と呼んでいます。メニューの
「共通の言葉」に並んでいるのが、いま使われているクラスと属性の一覧です。

語彙を他の人と揃えるほど、データはつながります。だから Asterism には、自分
のデータ専用の言葉を、世界で使われている標準の語彙（QUDT・schema.org など）
に結びつける機能があります（[vocab-and-grounding.md](./vocab-and-grounding.md)）。

## SPARQL — つながったデータへの問い方

Excel に対する検索やフィルタにあたるものが、つながったデータにもあります。
それが **SPARQL** です。3 つ組の「わからないところ」を `?名前` にして書く
と、あてはまる組み合わせを全部返してくれます。

```sparql
SELECT ?料理 ?分量 WHERE {
  ?使用量  recipe:食材   ?食材 .        # 食材が
  ?食材    schema:name  "にんじん" .    # にんじん であるものを探し
  ?使用量  recipe:料理   ?料理 ;        # その料理と
           recipe:分量   ?分量 .        # 分量を返す
}
ORDER BY DESC(?分量)
```

Asterism では、SPARQL を自分で書く必要はありません。メニューの「質問する」
でふつうの言葉で聞けば、内部でこの問い合わせが組み立てられ、答えと一緒に
出どころが返ります。SPARQL を直接書きたい場合の入口も、データセットの
「ツール」タブに用意されています。

![「ツール」タブ。このデータで答えられる問い合わせの一覧](../screenshots/dataset-tools.png)

## 用語の関係

ここまでの言葉は、次の関係にあります。

![書き方の決まりと語彙が合わさって実際のデータになり、そのデータに SPARQL で問う関係の図](../figures/terms.svg)

読み下すとこうなります。

- **RDF** は書き方の決まり、**IRI** はそこで使う名前のつけかた
- **オントロジー**はどんな**クラス**と**属性**を使ってよいかの語彙
- 決まりに従って語彙で書いた**事実**の集まりが、実際のデータ
- そのデータに問うための言葉が **SPARQL**

## 画面の言葉との対応

Asterism はこれらの用語を、なるべくやさしい言葉に置き換えて表示しています。
文献や他のツールを読むときのために、対応を挙げておきます。

| Asterism の画面 | 標準の用語 | ひとことで言うと |
|---|---|---|
| 事実 | トリプル（triple） | 3 つ組ひとつ = 事実 1 件 |
| データの種類 | クラス（class） | 料理・食材などの区分 |
| 項目 | 属性 / プロパティ | 種類が持つ列にあたるもの |
| ID・ID のつけかた | IRI・IRI テンプレート | 世界でひとつの名前 |
| 共通の言葉 | オントロジー / 語彙 | 使ってよいクラスと属性の一覧 |
| つながり | 参照（オブジェクト属性） | 別のものを IRI で指すこと |
| 高度な検索（SPARQL） | SPARQL クエリ | つながったデータへの問い合わせ |
| 変換ルール | RML マッピング | 表を 3 つ組に変える規則 |
| 公開する | 昇格（promote） | 引用できる状態にすること |
