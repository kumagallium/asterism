# ID の引っ越し — 公開したあとに「データの数えかた」を直せるようにする

Status: accepted (2026-08-27)

関連 ADR: [`kantan-mode-two-tier-ux.md`](kantan-mode-two-tier-ux.md)（K21・K10）/
[`instance-iri-base.md`](instance-iri-base.md)（IRI の不変性・`/describe`）/
[`phase5-declarative-substrate.md`](phase5-declarative-substrate.md)（version graph と promote）

## 1. 問題

かんたんモードは公開後の再設計で、**意味と単位は直せるが、種類と ID は直せない**。
`KantanWizard` の `canBackToGate` が `!redesigning` を含んでいて、S4「データの
数えかた」へ戻る導線が公開済みデータでは出ない。

閉じていた理由は正しかった。「データの数えかた」をやり直すと Mapping IR の
subject template が変わり、**同じ行から違う IRI が作られる**。IRI は「引用できる
事実」の住所そのものなので（`instance-iri-base.md`）、住所の作り方を変えることは
配った引用を切ることを意味する。K21 が「**後から意味（label）を足しても IRI は
直らないので、直せるのは作られる前だけ**」と書いたのと同じ理由である。

実装レベルでも、切れ方は静かで確実だった:

| 段階 | 起きること |
|---|---|
| 再取り込み | 新しい version graph `canonical/{id}/v{n+1}` に **新しい IRI** で入る |
| 公開（promote） | `liveGraph` が新 version を指し、**旧 version は `pendingDrop` へ**（`substrate.promote_to_canonical`） |
| 背景の掃除 | 旧 version graph が DROP され、**旧 IRI のトリプルが物理的に消える** |
| 旧 IRI を開くと | `/describe` が「まだ公開されていないようです」と 404 を返す |

つまり利用者から見ると、引用リンクが**理由の分からない 404 になる**。

一方で、直せないこと自体が実害である。ユーザー要望（2026-08-27）:
「種類や ID は後から修正できるようにできないのですか？ して良いことなら
できるようにしてほしい」。数えかたの誤り（500 行が 1 件に潰れていた、
1 行 = 1 試料にすべきだった）は、**公開して使ってみて初めて分かる**ことが多い。

## 2. 決定 — ID の引っ越し（転送台帳）

**IRI は書き換えない。旧 IRI を残したまま、行き先を指す小さな事実を別に持つ。**
これは `instance-iri-base.md` の「IRI immutability holds」に反しない ——
むしろ、旧 IRI が黙って消えるのを止めるので、不変性を強化する。

機械は旧設計と新設計を**両方**持っている。だから旧 IRI → 新 IRI の対応は
推測ではなく決定論で作れる:

| 層 | 実装 | 要点 |
|---|---|---|
| 計画 | `step0/id_move.py` の `plan_id_move` | 旧「ID の作り方」と新 Mapping IR を突き合わせ、動く／動かない／繋げないを出す。純粋関数 |
| 台帳の生成 | `compile_id_move_rml` → 既存の `rml_compile` → Morph-KGC | **旧 template を subject、新 template を object** に置いた RML を組み、同じソースをもう一度流す |
| 置き場 | `…/asterism/graph/moved/{dataset_id}` | version graph の**外**。追記のみ。Ask / FROM-merge のスコープには入れない |
| 読み出し | `substrate.follow_id_move` → `/describe` | 見つからない IRI だけが台帳を引く。推移的に辿り、**公開スコープに実在するもの**に着地する |
| 人への提示 | S8 の「ID の引っ越し」カード + `GET /api/datasets/{id}/id-move` | 公開ボタンを押す前に「N 件の ID が変わります」を見せる（K10 の流儀） |

台帳の RML はこの形になる（実測。`{SID}` だけで数えていたのを `{SID}-{sample_id}` に直した場合）:

```turtle
<#IdmoveSampleMap> a rr:TriplesMap ;
  rml:logicalSource [ rml:source "samples.csv" ; rml:referenceFormulation ql:CSV ] ;
  rr:subjectMap [ rr:template "https://…/resource/sample/{SID}" ] ;
  rr:predicateObjectMap [ rr:predicate <http://purl.org/dc/terms/isReplacedBy> ;
    rr:objectMap [ rr:template "https://…/resource/sample/{SID}-{sample_id}" ;
      rr:termType rr:IRI ] ] .
```

**IRI の綴りをこの機構が自分で組み立てない**のが肝心な点である。旧 IRI も新 IRI も
同じコンパイラ・同じ Morph-KGC が作るので、「台帳の言う旧 IRI」と「かつて公開した
IRI」がずれる余地が構造的に無い。生成された RML は既存の `assert_rml_safe` /
`validate_rml_design` をそのまま通る（防御の重ね掛けは無傷）。

## 3. なぜ `owl:sameAs` ではないか

述語は **`dcterms:isReplacedBy` 一本**。`owl:sameAs` は採らない。

決め手は「ID の作り方を変えると **1 対 1 とは限らない**」という事実である。
実データ（`starrydata_min`）で確認した:

```
<…/sample/1> dcterms:isReplacedBy <…/sample/1-10> .
<…/sample/1> dcterms:isReplacedBy <…/sample/1-11> .
```

論文単位で数えていた 1 件が、試料ごとに数え直して 2 件に分かれた。ここで
`owl:sameAs` を使うと「`sample/1-10` と `sample/1-11` は同じもの」という
**嘘の事実**を公開することになる（sameAs は対称・推移的なので、両者が融合する）。
本プロダクトの主軸は「引用できる事実」であり、嘘の事実を 1 件でも公開しないことが
相互運用性より優先する。

| 述語 | 1→多（分かれた） | 多→1（まとまった） | 推論への波及 |
|---|---|---|---|
| `owl:sameAs` | **嘘になる** | 嘘になる | 全グラフに波及 |
| `dcterms:isReplacedBy` | 「N 個に分かれた」と読める | 「同じ先にまとまった」と読める | 無し（向きを持つだけ） |

「1 対 1 のときだけ sameAs も併記する」案も検討したが、採らない。同じ台帳に
2 種類の述語が混在すると「なぜこの行だけ 2 本あるのか」を人に説明する必要が生まれ、
決定論の説明可能性を落とす割に、得られるのは限定的な自動推論だけである。

## 4. 「公開した時点の ID の作り方」をいつ記録するか

比較の相手は「**公開したときの**設計」でなければならない。再設計が保存された
あとに保存済み設計を読むと、それは**置き換えた側**を指してしまう。

| タイミング | 何をするか | なぜ |
|---|---|---|
| promote（公開） | `meta.published_subjects` に subject だけ記録（`registry.mark_promoted`） | これが正本。公開の瞬間に街に出た「作り方」そのもの |
| 再設計の上書き直前 | 未記録かつ公開済みなら、いまの設計から backfill（`backfill_published_subjects`） | この機構より前に公開されたデータも、最初の再設計から機能する。この瞬間は保存済み設計 = 公開済み設計 |
| ingest（再取り込み） | 台帳を作り、実測件数を `meta.id_move` に記録 | 「N 件動きます」は計画値ではなく**実測**。リロードしても同じ答えが出る |

backfill は**既存の記録を絶対に上書きしない**。上書きできると、後から来た再設計が
自分の subject を「公開したもの」として滑り込ませられてしまう。

記録するのは subject（`template` + `transform`）だけで、設計まるごとではない。
IRI の綴りを決めるのはそれだけであり、プロパティ・ラベル・単位をいくら変えても
住所は動かない。template は **CURIE を展開した絶対 IRI** で持つ —— prefix 名は
K13 が slug から決定論で導出するので設計のやり直しで変わりうるが、住所は変わらない。

## 5. 「引っ越せない」を一級の結果として扱う

前の住所が開けなくなることは、黙って起こしてよい事ではない。計画は 3 つに分けて返す:

| 結果 | 意味 | 画面 |
|---|---|---|
| `moved` | 住所が動き、転送も書ける | 「N 件の ID が変わります。前の ID を開いた人は、引き続き新しい内容にたどり着けます」 |
| `unchanged` | 住所は動かない | 何も出さない（意味・ラベルだけの修正がこれ） |
| `blocked` | 動くのに転送が書けない | **警告色**で「前の ID からたどれなくなります」＋ 理由＋戻り道 |

`blocked` の理由は 2 つだけである。`no_matching_map`（その種類が設計から消えた =
行き先が無い）と `missing_columns`（旧 ID を綴る列がいまのファイルに無い）。
列の判定は `rml_validate.read_csv_header` —— **取り込みゲートが使うのと同じ
ヘッダ読み**を通す。人に見せた判定と、直後にエンジンが到達する判定が食い違っては
ならないからである。

`blocked` があっても公開は**止めない**。止めるべきかは所有者の判断であり、
機械が代わりに決めることではない（K22 と同じ立場）。

## 6. 読み出し側 —— 配った引用が何を返すか

`/describe` は、公開スコープに何も無いときだけ台帳を引く。生きている ID は
これまで通り直接答える（台帳は「見つからない」ときだけの道）。

| 状況 | 応答 |
|---|---|
| 行き先が 1 つ | 新しい ID の中身を表示 ＋ **たどってきた前の ID を明示**（黙って転送しない） |
| 行き先が複数 | 「この ID は、いくつかの ID に分かれました」＋ 全部を一覧（どれか 1 つを勝手に選ばない） |
| 行き先が未公開 | 「引っ越しましたが、引き継ぎ先が公開されていません」（ただの 404 にしない） |
| 台帳が知らない | これまで通り 404（引っ越しの仕掛けが「見つからない」を曖昧にしない） |
| `Accept: text/turtle` | `dcterms:isReplacedBy` を返す（機械も同じ答えを追える） |

**チェーン（v1→v2→v3）** は推移的に辿る。各再取り込みはその回の old→new しか
書かないので、v1 の ID は「もうどのグラフにも無い v2 の ID」を経由して v3 に届く。
だから追跡は「台帳が名前を挙げ、かつ公開スコープが実際に記述している ID」に
着地するまで進む（上限 8 ホップ・訪問済み集合でループ終端・行き先 50 件で打ち切り）。
これが台帳を version graph の**外**に置いた理由でもある —— 中に置くと、次の
promote が転送記録ごと落としてしまい、まさに防ごうとした故障が起きる。

## 7. 変えないもの（不変条件の確認）

- **IRI の不変性**: 既存グラフを書き換えない。台帳は別グラフの追記のみ。
- **決定論**: LLM は 1 回も呼ばない。計画も台帳も旧新 2 つの設計と元データから出る。
- **実行安全**: 生成コードは走らない。台帳の RML も Tier 0 閉集合 + 既存の
  安全ゲート（`assert_rml_safe` / `validate_rml_design` / 422 ハードゲート）を通る。
- **Ask の答え**: 台帳は canonical / FROM-merge スコープに入れない。転送は
  「データがどう作り直されたか」であって、誰かが尋ねた事実ではない。
- **人間ゲート 3 つ**: 増やしていない。S8 の公開ゲートに情報を 1 つ足しただけ。

## 8. K21 の改訂

K21 の「**直せるのは作られる前だけ**」は、**label について**は今も正しい
（ラベルを足しても IRI は直らない）。改訂されるのは「だから公開後に S4 へ
戻れない」という帰結の部分である。

> **K21 改訂（2026-08-27）**: 公開後も「データの数えかた」に戻れる。ID の作り方が
> 変わった場合は、旧 ID → 新 ID の転送を決定論で作り、旧 ID を開いた人が新しい
> 内容にたどり着けるようにする。転送を書けないぶんがあるときは、公開の直前に
> 件数と理由を人に見せ、進むかどうかを人が決める。名前を**作られた瞬間に**
> 聞く（K21 本体）ことの価値は変わらない —— 引っ越しは事故の後始末であって、
> 最初から正しい名前が付く方が常に良い。
