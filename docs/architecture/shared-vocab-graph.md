# 共通の言葉のグラフ化 — 育つ地図

- 状態: 承認（2026-09-02 モック合議。モックは本番実データ 2 件で作成し、構成 2 点を利用者が裁定）
- 関連: `deterministic-design-assembly.md`（決定論の方針）, `external-standard-alignment.md`（接地）, `phase5-declarative-substrate.md`

## 背景

「共通の言葉」ページは語の**リスト**（種類・項目・外の語彙の一覧）で、Asterism の中心価値
——データセットがつながるほど育つボトムアップのオントロジー——が**構造として見えない**。
S（種類）- P（項目）- O（行き先）は保存済みの取り込みルールにすべて入っており、
⑤・データセット詳細では 1 データセット分を `rulesShape` で既に描いている。
足りないのは**横断**: 複数データセットをひとつの地図に重ね、標準語彙との接点と
データセット間の対応を同じ画面に置くこと。

## 決定

### 1. ページ構成（利用者裁定）

- **グラフが主役、リストは下に残す。** 既存の修正導線（名前が未設定 など）はリスト側に残る。
- **接地の候補も描く**（確定接地だけでは帯が空のままになる）。候補は AI ではなく
  決定論の照合で出す。

### 2. 絵の言葉（モックで合議した視覚言語）

| 要素 | 描き方 | データ源 |
|---|---|---|
| データセット | 点線枠のクラスタ＋名前・件数 | カタログ一覧 |
| 種類（クラス） | 箱。項目（リテラル）は箱の中（先頭数個＋「…ほか N 項目」） | 取り込みルール |
| データ内のつながり | 灰の実線・述語ラベル | 取り込みルール（`rulesShape` と同じ判定） |
| 標準の言葉 | 画面下の琥珀の帯（「地面」）。箱は琥珀 | known_vocabs + QUDT |
| 標準語の使用（確定） | 緑の実線 | ルール中の既知名前空間の述語/クラス |
| 接地の候補 | 琥珀の点線＋「候補」 | `ground_terms` score ≥ 90（exact 級）のみ |
| データセット間の対応 | 青（crosswalk 色）の点線・両向き | alignment グラフ |

### 3. 実装方針

- **すべて決定論・読み取り専用。LLM は使わない。**
- 合成は純関数 `ui/src/vocabGraph.ts` の `composeVocabGraph()`（単体テスト対象）。
  入力: 各データセットの `DatasetRules`・`getSchema()` のクラス件数（データセットごとの件数は §5）・alignments・
  接地候補。出力: クラスタ付きの Shape（節・辺・クラスタ）。
- 描画は新部品 `VocabGraph.tsx`（React Flow）。**`ShapeGraph` は触らない** —
  ④⑤が使う共有部品に横断図専用の概念（クラスタ・辺種別）を混ぜて退行させない。
  箱の見た目・段組みと線の通り道の計算（`arrange()`）・枠の中の線の部品
  （`ShapeEdgeLine`）は共有する（2026-09-30 から。kantan K54 の追記）。
- 接地候補の一括取得に `POST /api/ground/terms` を追加（語のリスト → 語ごとの候補。
  既存 `GET /api/ground` のループをサーバ側で回すだけ。閉集合・決定論・読み取り専用）。
  1 語 1 候補・score ≥ 90 を既定にする — 弱い一致まで描くと地図がノイズになる。

### 4. 描かないもの

- 実体（ABox）の個々の件。件数だけを箱に書く（§5 のデータセット単位の件数）。
- 両端が解決できない対応（削除済みデータセットの語など）。事実だけを描く。
- rdf/rdfs/owl の配管語彙（現ページの PLUMBING 方針を踏襲）。ただし述語としての
  使用が既知名前空間（dcterms 等）に当たる場合の「使っている」線は描く。

### 5. 箱の件数はデータセット単位で引く（2026-10-07）

箱の件数を `getSchema()`（`schema_summary`）から引くと 2 つの穴があった:
(1) 全データセットを混ぜた合計なので、同じ種類 IRI を 2 つのデータセットが使うと
どちらの箱にも合計が出る。(2) 上位 50 種類で切られ、件数の少ない種類の箱は黙って欠ける。

- **新しい読み手** `asterism.kind_counts.kind_counts` と `GET /api/kinds/counts`。
  公開済みの版 graph とハブ graph（`canonical_graphs`）を 1 本の SPARQL で
  `GROUP BY ?g ?c` し、`{graphs: [{graph, dataset_id, hub, kinds}], truncated}` を返す。
  `dataset_id` は版 graph から引いた**登録 id**（ハブは `null`）。行数の上限
  （既定 5000）を超えたら `truncated: true`。公開 0 件なら SPARQL を投げず空を返す
  （空の `FROM NAMED` は draft まで読むため）。
- **UI**: `composeVocabGraph` は `classCountsByDataset`（節のデータセット id → 種類 IRI →
  件数）が渡されたらそれだけを引き、全体の合計を混ぜない。API が取れなかったとき
  （失敗・古いサーバ・上限で切れた `truncated`）だけ従来の `classCounts` に落ちる。
- ⭐**id の取り違え**: API の `dataset_id` は登録 id で、カタログの `id` は `live-<登録 id>`。
  `classCountsByCatalogId` が `datasetApiId` を通して突き合わせる（これを怠ると一致が 0 件に
  なり件数が全部消える — `ui/src/vocabGraph.ts` 冒頭の「地図が空だった」事故の注記と同じ型）。
- 見た目は変えない（数字が正しくなるだけ）。この件数は案 B（TBox の全体図）の土台でもある。

### 6. 「全体」表示（案 B・2026-10-07・2 段に作り直し）

「共通のことば」の地図に表示の切り替え「全体 ／ 詳しく」を足した（新しい画面・3 つ目の地図は作らない）。
既定は「全体」（全体 → 詳細の順で見せる）。選んだ方は localStorage に覚える（保存できなくても動く）。

#### 6.0 規模試験の結果（作り直しの理由）

作り物のデータで 4 段の規模を測った（配置の計算・実画面の撮影・コード解析）。最初の版（全部を 3 列の丸で描く）の結果:

| 規模 | データセット・種類 | 図の大きさ | 名前の字（通常表示） | 線の交差 |
|---|---|---|---|---|
| S | 5・25 | 1460×1172 | 5〜6px | 9 |
| M | 20・160 | 1460×3952 | 約 2px | 357 |
| L | 50・600 | 1460×12858 | 縮小の下限 0.08 で止まり窓に収まらない | 3,200 |
| XL | 100・2000 | 1460×38804 | 同上 | 32,772 |

原因は 2 つ。(1) データセットの枠を左右 2 列に縦に積むので、幅は 1460 で止まり高さだけが伸びる。(2) 線がまっすぐで何もよけず、
交差がデータセット数のほぼ 2 乗で増える。見本の 4 データセットでも、つながりへの線 9 本のうち 3 本が別の丸の後ろを通った。
そこで**描く単位を規模に合わせて 2 段にする**（利用者の判断「おすすめで」）。

#### 6.1 2 段の描き方

- **段の決め方（決定論）**: データセット 6 以下かつ種類の合計 40 以下（`KIND_LEVEL_MAX_DATASETS = 6`・`KIND_LEVEL_MAX_KINDS = 40`・
  種類は `rulesShape` で畳んだ数）なら**種類まで**。超えたら**データセットごと**。見本（4 データセット・8 種類）は種類まで。
- **種類まで（`layoutKindOverview`）**: 種類を**丸**で、データセットの枠で、ハブを真ん中の列の丸で描く。
  いまの「3 列」はこの段の配置として残る（全体を 3 列で描くのは小さいときだけ）。丸の半径は §6.3（表示している中の最小〜最大で対数・
  16〜52・ハブは別のスケール）。標準のことばは一番下の帯。項目（フィールド）は描かない。
- **データセットごと（`layoutDatasetOverview`）**:
  - 丸は 1 データセット 1 つ（大きさ = 種類の件数の合計・§6.3 のスケールで 16〜56）。名前は丸の下 2 行まで、その下に「N 種類・M 件」（丸の中に件数が出るときは「N 種類」だけ）。
  - 図の縦の真ん中に**つながりの帯**（ハブを横に並べる）。データセットは帯の**上と下に行で並べる**（入力順に上・下へ交互・
    帯に近い行から詰める）。1 行の数は図の幅（目安 1400px）÷ 升の幅（max(丸の直径, 名前の幅 112) + 16）。
  - **並び（交差を減らす・決定論）**: Sugiyama の片側交差削減を 4 往復。ハブの初期は名前順 → 各行のデータセットをつながる
    ハブの x の平均（重心）で並べ替え（同点・つながり無しは入力順・つながり無しは段の最後の行へ）→ ハブをつながるデータセットの
    x の平均で並べ替え（同点は名前順）→ これを 4 回。乱数・時刻は使わない。
  - **線**: データセット → ハブを 1 本（何種類参加していても 1 本・title に「N 種類が参加」）。対応（alignment）は
    両端のデータセットが違うものだけ、データセット ↔ データセットの点線 1 本。標準のことばはこの段では描かない。
  - 高さの目安は 100 データセットで約 1,500px 以内（テストで固定）。1400px の幅で収まらないときは、行の数を減らすために
    幅を 200px ずつ広げる（上限 4000px）。
- **周りだけ開く（フォーカス）**: 俯瞰でデータセットかハブを押すと、その周りだけを**種類まで**描く。入力を絞るだけで配置関数は
  変えない（`focusOverview`）。データセット D = D の全部の種類 + D が参加するハブ + そのハブの他の参加者の参加している種類だけ。
  ハブ H = H + 参加する全部のデータセットの参加している種類だけ。省いた種類は枠に「ほか N 種類」。上に「全体に戻る」と
  「〇〇の周り」。フォーカスの状態は `VocabMapSection` が持ち、「大きく見る」の重ね表示にも渡す。
  **周りの図にも上限を置く**: 種類まで図は 2 列に縦積みなので、参加者が多いと高さだけが伸びる（規模試験: ハブ参加 30・
  データセット 100 で、D を押すと 92 枠・高さ 11,736px）。そこで他のデータセットは `FOCUS_MAX_DATASETS = 8` 個まで
  （選んだハブを共有する数の多い順・同数は入力順）、D を押したときのハブは `FOCUS_MAX_HUBS = 6` 個まで（参加者の多い順）に絞り、
  残りは上の帯に「ほか N 個のデータセット／つながりは省いています」と書く（同条件で高さ 約 2,200px 以内）。
- **線の強弱**: 丸・ハブにマウスを載せたとき、その丸につながる線を濃く（`is-hot`）、他を薄く（`is-dim`）。React Flow の
  `onNodeMouseEnter`／`onNodeMouseLeave` で強調する id を持ち、線の className で切り替える（CSS のホバーは線に届かない）。
  何も載せていなければ今の濃さ。強調する id は図（layout）とセットで持ち、図が切り替わったら無効（押した丸が消えて
  mouseleave が来なくても薄いまま残らない）。線の title「N 種類が参加」は、選べない線に React Flow が付ける
  `pointer-events: none` を、見えない当たり判定の線（`.react-flow__edge-interaction`）だけ CSS で戻して受ける。
- **線は端点でない丸をよける（2026-10-09）**: 以前は線が直線で、別の丸の裏を通ることがあった（測定: 24 本中 2・75 本中 43・
  180 本中 133 本。作り物の規模で、中心から中心の直線が端点でない丸の中に入る本数）。利用者の報告「SpaceGroup は Card からつながっているはずが、ChemicalFormula からつながっているように見える」
  （xrd-cards で Card・ChemicalFormula・SpaceGroup が同じ行に並び、Card→SpaceGroup の直線が ChemicalFormula の中心を通る）を受け、
  純関数 `routeAround`（`kindOverview.ts`）で**二次ベジェに曲げる**。よけるもの（障害物）は、端点でない丸（種類の丸・ハブの丸／
  データセットごとはデータセットの丸・ハブの丸）と、**その下の名前**（`labelRect`。11px・行 14px・2 行まで＋件数の行 15px を、
  字の幅の見積もり〈全角 = 字の大きさ・半角 0.62 倍〉で四角にしたもの）と、端点でない**枠の題**（`frameTitleRect`）。端点の丸の名前は
  除く（下へ出る線は必ず通る）。枠・標準のことばの箱そのものは障害物にしない。
  直線が障害物から 6px 以上離れていれば直線のまま。そうでなければ中点から法線（from→to の左を ＋）へ頂点を 14px の倍数で
  `+1, −1, +2, −2, …`（最大 8）ずらして試す。選び方は**丸を先に**: (1) 丸からも名前からも離れる最初のもの、(2) 無ければ丸からは
  離れるもののうち名前の余白が最大のもの（直線が丸から離れているなら、直線より名前の余白が大きいときだけ曲げる）、(3) 丸からも
  離れきらなければ丸の余白が最大のもの（直線より悪ければ直線のまま）。同点は試した順で先。乱数・時刻なし（決定論）。
  判断は**実際に描く線**（両端を制御点へ向かう縁にそろえた曲線）で行う（中心どうしの曲線で判断すると、描く線が丸に入ることがあった）。
  曲線は長さ 4px ごと（最低 24 点）に調べ、曲線の外接四角に掛かる障害物だけを見る（規模が大きいときの速さ）。丸の配置は変えない。
  直した後の測定（作り物の規模・実際に描く線を 401 点で調べて内側〈余白 0〉に入る本数、直線 → 曲げた後）:
  丸 = 24 本 2 → 0・75 本 43 → 12・180 本 133 → 75／名前 = 6 → 1・46 → 32・136 → 120（テストで数値を固定）。
  密な規模ではまだ残る（よけきる空きが無い／よけた先が別の丸や名前に当たる）。
- **集計の帯**: 種類まで = データセット・種類・つながり・標準・件数の合計／データセットごと = データセット・種類（合計）・
  つながり・件数の合計／周り = データセット・種類・つながり。

#### 6.2 共通の決め事

- **データ（API は増やさない）**: 既存の取り込みルール・件数（`/api/kinds/counts`・データセット単位）・対応・接地の名前に、
  `GET /api/crosswalks` を 1 回足す。同じデータセットで同じ種類を名乗る map は `rulesShape` の畳み方（K63）で 1 つの丸にし、
  種類どうしの線も `rulesShape` の辺（`linksTo`）をそのまま使う。ハブ = つながりの概念ごとに 1 つ、大きさ = ハブの graph の
  `class_iri` の件数。種類 → ハブの線は参加者の（登録 id, `subject_class`）が合う丸から（`subject_class` が無い参加者は枠から）。
  対応は片端が種類の丸のものだけ（項目どうしの対応は描かない）。
- **役割の違い**: 3 つの地図は問いが違う。つながりの地図（3 レーン）は「何と何がつながっているか」、「詳しく」は
  「どの項目がどの標準のことばに合っているか」、「全体」は「どのデータセットにどんな種類がどれだけあり、何でつながるか」。
- **力学配置を採らない理由**（維持）: 箱が開くたびに動くと、人が覚えた位置が毎回変わる。Asterism の他の図はすべて決定論
  （並びは入力順と辞書順・重心の平均）で、写真・テスト・再現が揃う。種類まで = 3 列（左のデータセット・ハブ・右のデータセット、
  入力順に左右交互）と枠の中の件数順・1 行最大 4 つ。ハブはつながる枠の中心の高さの平均が近い順。線は直線だが、端点でない丸や
  その下の名前を通るときだけ二次ベジェで曲げる（§6.1）。
- **標準のことばを外周に回さない理由**: 外周に置くと線が長く、丸や枠をまたいで交差しやすい。既存の地図と同じく下の帯に
  横並びにする（種類まで の段だけ）。
- 実装: 純関数 `ui/src/kindOverview.ts`（種類までの配置・線）・`ui/src/kindOverviewScale.ts`（段の選び方・
  データセットごとの俯瞰・フォーカス・線の強弱・交差の数）、描画 `ui/src/KindOverviewMap.tsx`、切り替え `VocabMapSection.tsx`。
  押すと、種類までの段は丸 → 種類のページ・枠 → データセット・ハブ → つながり。データセットごとの段はデータセット・ハブ → 周りを開く。
  「大きく見る」は共通部品 `BigView.tsx`（O67）。
- **名前は丸の下**（2 行まで・地の色で縁取り）。丸の中に入れると、件数の少ない小さい丸（半径 16）で字が切れ、
  ハブの名前まで読めなかった（実機の見本で発見）。升の幅は名前の幅（種類 104・ハブ 132・データセット 112）で取る。
- **集計の帯は表示ごとに数える**。図に描いたものだけを数える（「詳しく」の数字を「全体」の上に出すと、図に 1 つしか描かない
  標準を 8 と数えるような食い違いが出る）。

#### 6.3 丸の大きさ（#689）

- **なぜ頭打ちをやめたか**: 以前の半径 = `16 + 10·log10(件数 + 1)` は 1 万件で上限（種類 52・データセット 56）に当たった。
  数百万件の実データではどの丸も同じ大きさになり、大きさが何も語らない。しかも半径が対数に比例するので面積は対数の 2 乗で、
  小さな差を誇張していた。
- **決め方（`sizeScale(counts, rMin, rMax)`・純関数）**: `t = (log10(n+1) − log10(min+1)) / (log10(max+1) − log10(min+1))`
  （min・max は**件数のある丸だけ**）。**面積を対数に比例させる**ため `r = rMin + (rMax − rMin)·√t`。件数のある丸が 1 つだけ・
  全部同じなら中間（√0.5）。件数の無い丸（未取得・0 件）は rMin で件数の字なし。半径の範囲は変えない（種類 16〜52・
  データセット 16〜56・ハブ 16〜52）。
- **スケールを取る範囲＝その図に描くもの**: 種類までの図（全体・周り）は種類の丸で 1 つ、ハブはハブの件数で別。データセットごとの
  俯瞰はデータセットの丸（種類の件数の合計）で 1 つ、ハブは別。配置は並べる前に全部の件数からスケールを作る（決定論）。
- **表示ごとのスケールなので、同じ件数でも図で大きさが違う**（全体と周りでは描くものが違う）。大きさは「この図の中での比べ」で、
  **件数は字で読む**: 半径 22 以上の丸は丸の中に短い形（`Intl.NumberFormat` compact・ja「120万」・en「1.2M」）、
  それ未満は名前の下に「N 件」。title は常に正確な数。データセットの丸は中に件数が出るとき下は「N 種類」だけ。

#### 6.4 色と面（#689）

- 白の丸と点線の枠は下書きに見えた。**役割の色でうすく塗り**、既存のトークンだけを使う（新しい色は作らない）。
  種類の丸 = `--primary-soft`＋`--primary` を薄めた縁・字は `--primary`／データセットの丸 = `--primary` 18% を `--surface` に混ぜた
  少し濃い緑／つながりの丸 = `--activity-soft`＋`--activity`。載せた丸は縁が不透明になり薄い影。
- 枠 = `--surface` の面＋`--border` 1px 実線・角丸 10px。つながりの帯・標準のことばの帯 = `--activity-soft`／`--accent-soft` を
  薄めた面（枠線なし）。変えるのは全体図だけで、「詳しく」（`VocabMap`）の見た目は変えない。
- 線: 種類どうし = `--border-strong` の実線、つながりへの参加 = `--activity` 55% の実線、標準のことばを使う線 = 実線の琥珀（細め）。
  全体は**確定の使用だけ**を描くので実線にした。**点線は「詳しく」の「候補」だけに残る**。対応 = 青の点線のまま。
- **データセットごとの色分けをしない**: 100 データセットで色が足りず、似た色が並ぶと凡例なしでは読めない。区別は名前と位置で行う。

## 育ち方

データセットを公開するたびに箱と線が増える。同じ標準語に複数データセットの線が
集まった瞬間が「言葉が共有され始めた」目印で、この地図の存在理由。統計帯
（N データセット・M 種類・K 項目・接地・対応）が数字でも同じことを言う。
