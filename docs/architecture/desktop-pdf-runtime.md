# ADR: デスクトップ版の PDF 読み取り — Docling を「あとから入れる」

状態: **実装済（段 1・段 2）**（2026-10-05）。方式と入口の置き方は、利用者が図の比較から選んだ（§2・D6）。

関連: [`local-first-distribution.md`](local-first-distribution.md)（§6.3 置く前に伝える・§7 残）/
[`pdf-docling-conversion.md`](pdf-docling-conversion.md)（サーバ版の PDF 変換＝サイドカー）/
[`ingestion-execution-safety.md`](ingestion-execution-safety.md)（生成コードを実行しない）。

## 0. 一行サマリ

デスクトップ版は、利用者が設定で 1 回ボタンを押すと **PDF を読み取る部品（Docling の実行環境と
モデル・約 1.7GB）を手元に取得**し、以後はアプリが **Docling サイドカーを子プロセスとして起動**する。
変換は手元で完結し（PDF は外に出ない）、サーバ版と同じサイドカー・同じ決定論アダプタを通る。

## 1. 文脈

- サーバ版の PDF は、Docling（レイアウト解析の ML）を **別プロセスのサイドカー**に隔離している
  （`infra/docling-sidecar/app.py`）。api は `ASTERISM_DOCLING_URL` に PDF を渡し、返ってきた生の
  構造を in-repo の決定論アダプタ（`documents.docling_dict_to_jats`）で JATS にする。
- デスクトップ版はサイドカーを持たないので、PDF は取り込めない。画面は置く前にそう伝える
  （`/api/instance` の `can_convert_pdf`。local-first-distribution.md §6.3）。
- 手元の実測（Apple Silicon・docling 2.102.1・OCR なし・2026-10-05）:

  | 項目 | 値 |
  |---|---|
  | 実行環境（Python パッケージ 105 個・D2 の一覧で入れたもの） | 1.2GB（うち PyTorch が約 0.5GB） |
  | モデル（レイアウト・表） | 0.5GB |
  | 入れるのにかかる時間 | 96 秒（この Mac・この回線で。回線しだい） |
  | 変換（7 ページ・1.2MB の PDF） | 1.3 秒（モデル読み込み後）。最初の 1 回はモデルの読み込み込みで 13 秒 |
  | メモリの最大 | 1.7GB |
  | オフライン（`HF_HUB_OFFLINE=1`） | 取得済みのモデルだけで変換できる |

  全員に同梱するには大きい（同梱物は約 530MB）が、使う人だけが取得するなら現実的な大きさ。

## 2. 選ばなかった案

| 案 | 内容 | 選ばなかった理由 |
|---|---|---|
| 軽い読み取りを同梱 | ML を使わない読み取り（文字と書体の大きさから見出しを推定）をアプリに入れる | 段組・見出しの認識が粗い。サーバ版と別の変換器になり、同じ PDF から別の文・別の ID ができる |
| 読み取りサーバを使う | 設定にサイドカーの URL を入れる欄を足す | 未公開の PDF がそのサーバへ送られる。サーバを用意できる人しか使えない |
| 全員に同梱 | Docling をアプリに入れて配る | 配布物が約 2GB になる。PDF を使わない人にも負担になる |

「読み取りサーバを使う」は、env の `ASTERISM_DOCLING_URL` を自分で設定すれば今もできる（その場合、
本書の仕組みは何もしない＝D4）。

## 3. 決定

### D1. 置き場所 — データの保存先とは別にする

部品はデータではなくプログラムなので、利用者のデータの保存先（`~/Documents/Asterism` など。
NAS や同期フォルダのこともある）には置かない。

| OS | 場所 |
|---|---|
| macOS | `~/Library/Application Support/com.kumagallium.asterism/pdf-runtime/` |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/asterism-pdf-runtime/` |
| 上書き | env `ASTERISM_PDF_RUNTIME_DIR`（テスト・開発用） |

```
pdf-runtime/
  venv/            python -m venv（アプリの python を指す）
  models/          モデルの置き場（HF_HOME）
  runtime.json     何を入れたか（依存一覧のハッシュ・変換器の版・モデルのコミット・日時）
pdf-runtime.partial/   入れている途中。成功したら rename、失敗・中止・次回起動で消す
```

**自分が作ったものだけを使い、消す。** 置き場所は env で上書きできるので、指した先に別の物が
入っていることがあり得る。目印（`runtime.json` の `"kind": "asterism-pdf-runtime"`、`.partial` には
作った直後に置く目印のファイル）を確かめてからでなければ、「入っている」とみなさず、書き込まず、
消さない。目印の無いフォルダや symlink が在るときは、`failed`（「置き場所に別のものがあります」）に
して何もしない。消すときは中身を先に、目印を最後に消す（途中で止まっても、次に消し直せる）。

### D2. 入れ方 — アプリの python で venv を作り、ハッシュを固定した依存を入れる

- 同梱の CPython は `venv` と `pip` を持っている（確認済み）。追加のツール（uv など）は同梱しない。
- 依存は **版とハッシュを固定した一覧**（`api/src/asterism_api/pdf_runtime/requirements-macos-arm64.txt`・
  `uv pip compile --generate-hashes` で生成）から、`pip install --require-hashes --only-binary :all:`
  で入れる。ハッシュが合わないものは入らない。ソース配布物はビルドしない（任意コードを走らせない）。
- PyPI に wheel が無いパッケージが 1 つある（`antlr4-python3-runtime` 4.9.3。docling → rapidocr →
  omegaconf が要る。ソース配布物だけ）。これは、**ハッシュを確かめたソース配布物から作った wheel を
  同梱**し（`pdf_runtime/wheels/`・約 145KB・BSD。中の Python ファイルがソースと同一であることを
  確認）、`pip --find-links` で渡す。一覧のハッシュはこの wheel のもの。利用者の手元では何も
  ビルドしない。依存を更新するときは、wheel が無いパッケージが増えていないかを実際に入れて確かめる。
- pip のキャッシュは残さない（`--no-cache-dir`。利用者のキャッシュに約 1GB を置かないため）。
  その代わり、失敗したあとのやり直しは最初からになる（残 §6）。
- docling の版は、サーバ版のサイドカー（`infra/docling-sidecar/requirements.txt`）と同じ版に固定する。
  ずれたらテストが落ちる。
- 一覧があるプラットフォームだけが対応（いまは macOS arm64＝配布しているデスクトップ版と同じ）。
  それ以外は「対応していない」と返す。
- venv はアプリの python への symlink を持つ。同梱の CPython の場所にはパッチ版が入っている
  （`cpython-3.11.17-…` など）ので、**アプリの更新で場所が変わり、リンクの先が無くなる**ことが
  実際に起きる。起動時に venv の python が動くかを確かめ、動かなければ `python -m venv --upgrade`
  で付け直す（入れたパッケージは残る）。`venv --upgrade` は切れたリンクが残っていると失敗する
  ので、先に外す（実物で確認: 3.11.11 で作った venv を、リンクを切ってから 3.11.17 で付け直せる）。
- 取得は**利用者がボタンを押したときだけ**。空き容量（3GB 未満なら始めない）を先に確かめる。
  pip の一時ファイルも `.partial/tmp` に置く（空き容量を確かめたのと同じ場所に落ち、片付けで
  一緒に消える）。
- 子プロセス（pip・モデルの取得・サイドカー）に渡す環境は**許可リスト**（`PATH`・`HOME`・ロケール・
  証明書・プロキシと、こちらで入れる `HF_HOME` など）。親の `ASTERISM_*`（書き込みトークンや AI の
  キーを含む）・`HF_TOKEN`・`PIP_*` は渡さない。

### D3. モデル — コミットで固定し、変換時はネットワークを使わない

- docling 2.102.1 は、レイアウトのモデル（`docling-project/docling-layout-heron`）を `main` で、
  表のモデル（`docling-project/docling-models`）をタグ `v2.3.0` で取りに行く。`main` は動くので、
  入れた時期によって別のモデルになり得る。**同じ PDF から同じ構造・同じ ID を得る**ために、
  どちらも**コミットで固定**する（`pdf_runtime/models.json`）。
- 入れるとき: 固定したコミットを取得し、docling が探す名前（`main`・`v2.3.0`）がそのコミットを指す
  ようにキャッシュの参照を書く。そのあと `HF_HUB_OFFLINE=1` でパイプラインを初期化し、足りない
  ものが無いことを確かめる（足りなければ入れるのを失敗にする。黙って取りに行かせない）。
- 変換するとき: サイドカーは `HF_HOME=<pdf-runtime>/models`・`HF_HUB_OFFLINE=1` で動く。
  **PDF を変換している間、ネットワークには出ない。**
- サーバ版のサイドカーのイメージは、ビルドした時点の `main` を焼き込んでいる（コミット未固定）。
  同じコミットに揃えるのは残（§6）。

### D4. サイドカー — 既存のものを、そのまま子プロセスで動かす

- `infra/docling-sidecar/app.py` を**無改修で**使う（同梱物に `backend/docling-sidecar/app.py` として
  入れ、場所は env `ASTERISM_DOCLING_SIDECAR_DIR`。checkout では `infra/docling-sidecar/`）。
  決定論アダプタ（`docling_dict_to_jats`）も取り込み経路も、サーバ版と同じものを通る。
- 起動: `asterism-local` が、部品が入っていれば起動時に、入れ終わったらその場で、
  `<venv>/bin/python -m uvicorn app:app --host 127.0.0.1 --port <空き>` を起こし、`/health` を待って
  `cfg.docling_url` に入れる。以後 `/api/instance` の `can_convert_pdf` が true になる。
  終了時は Oxigraph・demo-agent と同じく止める。
- サイドカーは起動しただけではモデルを読まない（最初の変換で読む）。読んだあとは約 1.7GB を
  持ち続ける。使っていないあいだ手放す仕組みは残（§6）。
- サイドカーが勝手に落ちたら、その場で `failed` にして `cfg.docling_url` を外す（見張りの
  スレッドが終了を待っている）。自動では起こし直さない — 設定の画面から起こし直すか、
  消して入れ直す。
- 入れる・消す・起動時の処理は 1 つずつ（直列）。アプリの終了時は子プロセスをすぐ止め、
  Oxigraph の停止を待たせない。
- 利用者が `ASTERISM_DOCLING_URL` を自分で設定しているときは、そちらを使い、この仕組みは何もしない
  （状態 `external`）。

### D5. API — ローカルモードだけに生える

`asterism-local`（デスクトップ版）だけが持つ。サーバ版（`asterism-api`）には無い（404）＝画面は
「この環境では部品を入れられない」と分かる。

| 経路 | 内容 |
|---|---|
| `GET /api/pdf-runtime` | 状態を返す（下の表）。読むだけなので認証なし |
| `POST /api/pdf-runtime/install` | 入れ始める（書き込みゲート）。入れている最中なら同じ状態を返すだけ |
| `DELETE /api/pdf-runtime` | 入れている最中なら中止、入っていれば止めて消す（書き込みゲート） |

よそのサイトのページからの `POST`／`DELETE` は、ローカルモードの入口の門
（`local.LoopbackOriginGuard`）が断る。ローカルモードはループバックからの接続に書き込み
トークンをサーバ側で足すので、門が無いと、ブラウザで開いたよそのサイトから 1.7GB の取得や
削除を起こせてしまう。はじめはこの 2 経路だけに Origin の確認を入れたが、同じ穴が既存の
書き込み経路全体にあると分かり、別の PR（#679）で入口に門が入ったので、**経路ごとの確認は
外して門に一本化した**（門のほうが広く厳密: Host の確認・Sec-Fetch-Site・WebSocket も見る）。

状態は次の形で返す（`installed`＝目印つきの部品のフォルダが在る。`failed` のとき、画面が
「部品を消す」を出すかどうかに使う）。

| `state` | 意味 |
|---|---|
| `unsupported` | このプラットフォームの依存一覧が無い |
| `external` | `ASTERISM_DOCLING_URL` が外から設定されている |
| `absent` | 入っていない |
| `installing` | 入れている最中（`phase` = `packages` → `models` → `starting`、`bytes_done`／`bytes_total` は目安） |
| `starting` | 入っていて、サイドカーを起こしている最中（アプリの起動直後の数秒。「入れている最中」とは別にする＝毎回の起動で取得中に見えないように） |
| `ready` | 入っていて、サイドカーが応答している |
| `failed` | 入れるのに失敗した、入っているのに起動できない、サイドカーが落ちた、置き場所に別の物がある（`error` に理由、`log_path` に記録の場所） |

### D6. 画面（段 2）

- 設定の「このアプリ」タブに「PDF の読み取り」の節を足す（`GET /api/pdf-runtime` が 404・
  `unsupported`・`external` のときは出さない）。はじめは「PDF」という独立したタブにしたが、
  利用者の指摘（部品 1 つの話が「AI」「このサーバ」と同じ段に並ぶのは釣り合わない）で改めた。
  あわせて「保存先」タブも同じタブの節にし、**このパソコンに入っているアプリに関わるもの
  （アプリ情報・アップデート・保存先・PDF の読み取り）を「このアプリ」に集めた**（タブは 7 → 5）。
  サーバ版（ブラウザ）では、保存先と PDF の節が出ないだけで、タブの並びは同じ。入れる・進み具合・中止・消す・失敗時のやり直しは、すべてここにまとめる。
  失敗の画面には「もう一度入れる」と、部品が残っているときは「部品を消す」を必ず出す
  （入っているのに動かないとき、やり直しが同じ失敗を返すだけの行き止まりにしない）。
- 置く欄の案内は、部品を入れられる環境では「PDF は、読み取る部品を入れると取り込めます。」に
  変え、「設定を開く」を添える。置く欄からは直接入れない（利用者の選択 — 置く欄を重くせず、
  約 1.7GB の取得をうっかり始めないため）。
- 入れ終わったら、画面は読み込み直さなくても PDF を受け付ける（部品の状態が変わったら
  `/api/instance` を取り直す）。

### D7. 信頼モデル — 既存の不変条件をそのまま守る

- **生成コードを実行しない**: 入れるのは、版とハッシュを固定した既知のパッケージと、コミットを
  固定したモデルだけ。AI が書いたものは何も走らない。
- **ML は取り込みの実行環境に入れない**: Docling は別プロセス（サイドカー）のまま。api の python は
  torch を import しない。
- **読み取りのために PDF を外へ出さない**: この仕組みがネットワークを使うのは部品を取得する
  ときだけ（PyPI と Hugging Face から、利用者の操作で）。変換はオフライン。サイドカーは
  ループバックの空きポートで待ち受ける（Oxigraph・demo-agent と同じ「この Mac に居る者＝所有者」の
  信頼）。言えるのは読み取りの範囲まで — 取り込んだあとの文章を AI にどう渡すかは、この仕組みの
  外（画面とマニュアルの文言も「読み取りのために外へ送ることはありません」に留める）。
- 変換の来歴（`lit:DocumentConversionActivity`＝変換器と版）は、サーバ版と同じ形で残る。

## 4. 検証

- 単体: 状態の移り変わり（入れる・失敗時の片付け・中止・消す・起動時の残骸の掃除）を、実際の
  取得をしない差し替えで確かめる。依存一覧の docling の版がサーバ版と同じであること。API 3 経路。
- 実機: 手元の Mac で実際に入れ、PDF を置いて取り込み→公開まで通す。変換中にネットワークへ
  出ないこと（`HF_HUB_OFFLINE=1` で動くこと）。
- 結果は PR と `docs/ROADMAP.md`（2026-10-05 の log）に書いた。

## 6. 残

- サーバ版のサイドカーのイメージを、同じ依存一覧・同じモデルのコミットに固定する（D2・D3）。
  いまのイメージはビルドした時点の最新を入れているので、デスクトップ版と変換器の細かい版
  （docling-core など）やレイアウトのモデルが違い得る。
- 失敗したあとのやり直しを途中から続ける（いまは最初から取得し直す）。
- 使っていないあいだモデルを手放す（D4）。
- 入れてある部品が古くなったとき（アプリの更新で依存一覧が変わったとき）の案内と入れ直し。
  `runtime.json` に依存一覧のハッシュは残してあるので、見分けはつく。
- macOS arm64 以外（依存一覧を足せば対応できる）。
- Graphium との連携（利用者の意向。形は未定）。
- 部品が `ready` のあいだにサイドカーが落ちたとき、開いたままの画面はすぐには気づかない
  （設定を開く・読み込み直すと分かる。PDF を置いた場合は取り込みが接続エラーで止まる）。
