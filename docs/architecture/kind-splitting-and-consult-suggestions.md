## 1. きっかけ — 2 週間前と同じ問いに、まだ答えられていない

`column-ownership-and-growth.md` の冒頭は、この XRD 参考カードについての利用者の問い
だった（2026-08-14）:

> 今後も XRD カードを足す予定。この設計でよいか？ ── **足すなら物質とパターンを分け
> ないと、同じ Al3V が 2 件に割れる**

2026-08-30、同じファイルを **v0.24.0（#453「意味を先に、ID を後に」を含む）で設計し
直して実測した**。結果は二分された。

| | 旧設計（#453 以前） | v0.24.0 |
|---|---|---|
| 表の外の 17 列 | **1 列も記録されない** | **18 件すべて拾い、意味を付ける**（NIST カード番号 / 空間群 / 化学式（詳細）（簡易）…） |
| 種類の分かれ方 | カード 1 つ + ピーク | **ほぼ変わらず**。`Name` `Chemical Formula` `Formula` `Z value` は全て「この表全体」 |
| ID を与えた値 | なし | **`CSD` 1 つだけ**。組成・空間群・結晶系は選ばれない |
| AI 自身の出力 | — | `Sample` と `DiffractionPattern` が**同じ列で同じ 1 件**を作る二重記録 |

**「拾う」は良くなったが、「どう分けるか」は改善していない。** 意味を材料にしても、
骨格段は「何を独立した種類にすべきか」を決められていない。

そして人が手で直そうとすると、**いまの UI では直せない**ことが分かった。

## 2. 何が塞がっているか

S4 で人ができるのは 3 つだけで、いずれも**列を起点**にしている:

| 操作 | できること |
|---|---|
| `＋ この値を種類にする` | **列の値**を種類にする（組成 → 「組成」という種類） |
| 「載せる種類」の選び直し | その項目を**どの種類に載せるか**変える |
| 🗑 | 余分な種類を消す |

「カードと結晶は**同じ `No` を使うが別のもの**」── つまり **1 つのキーから 2 つの種類を
作る**操作が無い。しかも作ろうとすると止められる:

> `{{names}}` は、同じ列で同じ 1 件を作ります。1 つの種類を二度書いた形なので、
> 要らない方は 🗑 で消してください

**この判定はキーの同一性だけを見ており、持つ項目が重なるかを見ていない。** 結果、
本物の二重記録（`Sample` / `DiffractionPattern` = 同じ列を持つ）と、正当な分割
（カード / 結晶 = 項目が分かれる）が区別されない。

G6 は最初から後者を許している:

> a column another map owns appears here **ONLY as a link/join key**

禁じているのは**同じ事実が 2 箇所にあること**であって、キーの共有ではない。判定が
本来の意図より広く網をかけている。

## 3. 決定

### D1 重複判定を、項目の重なりまで見て絞る

```
同じキーで種類が 2 つ
  ├ 持つ項目が重なる    → 二重記録。いまどおり止める（K7 の確認ブロック）
  └ 項目が分かれている  → 意図的な分割。何も言わない
```

判定は**決定論**（各マップの `properties` の集合を比べるだけ・LLM 0）。

**警告を全部消す案は採らない。** 実測で AI は放っておくと本物の二重記録を出した。
網を外すのではなく、意図どおりに絞る。

### D2 相談ボタンを ①「どの種類が、どの項目を持つか」の直後に置く

いまの「AI にもう一度考えさせる」は、①の表・②の確認・データセット名の**後ろ**にあり、
`.app-main` を下までスクロールしないと見えない。**疑問が生まれる場所と、頼む場所が
離れている**（利用者指摘 2026-08-30）。

S3 の「空欄の意味を AI に相談して埋める」と同じ仕組み（`requestConsult(prefill)`）を
使う。prefill は今回実測で実際に詰まった 3 点:

| ボタン | prefill |
|---|---|
| 分け方を相談 | この表の項目を、どんな種類に分けるとよいか教えてください |
| つながりを相談 | 外のデータとつなげたい値はどれですか。ID を与えるべき項目を教えてください |
| 重複を相談 | 同じものを二度書いている種類があります。どちらを残すべきですか |

### D3 提案ブロックに `splits` / `owners` / `identifiers` を足す

相談チャットは既に**提案 → 人が反映**の仕組みを持つ（`suggestions` = 意味・単位、
`kinds` = 種類名）。ここに 3 つ足す:

```json
{"splits":      [{"from": "card", "name": "結晶", "columns": ["Cell", "Volume", "Z value"]}],
 "owners":      [{"column": "Radiation", "map": "measurement"}],
 "identifiers": [{"column": "Chemical Formula", "reason": "外のデータと同じ名前で呼ばれる"}]}
```

- `splits` — **同じキーから種類を分ける**。今回の実測で分かった不足。これが無いと
  D1 で判定を緩めても、人にも AI にも分ける手段が無い
- `owners` — 帰属の移動。S4 の「載せる種類」と同じ操作なので、**同じ分散クラス内に
  限る**制約（`meaning-before-identity.md`）をそのまま適用する
- `identifiers` — ID を与える候補。**`reason` を必須**にする（K22: 人が判断できる材料
  を出す。押させるのではなく、選ばせる）

いずれも適用は**決定論**。UI のチェックボックス／ドロップダウンを機械が動かすのと同じ
で、LLM の再実行は要らない（`own` を決定論化した G18 と同じ筋）。

### D4 人が空の種類を足せる逃げ道を残す

主役は D3（AI が提案 → 人は採用を決める）。ただし**今回 AI は分けられなかった**。
逃げ道が「設計をやり直す」しか無いのは重い（ADR 自身が「足りない種類は設計をやり直さ
ないと足せず」と認めている）。

**列を起点にしない「同じ ID で種類を足す」入口**を 1 つ足す。足した後の項目の移動は
既存のドロップダウンで足りるので、追加は入口だけ。

## 4. 非目標

- **ID の作り方（IRI テンプレート）は提案させない。** 公開後に動かせない不可逆な判断で、
  引用が壊れる（`id-move-after-publish.md` の台帳はあるが、壊さないのが先）。相談
  チャットの現行仕様（「ID の作り方や、取り込む/取り込まないの裁定はここでは提案しま
  せん」）を維持する
- **骨格段のプロンプト改善は別**。D3 は「AI が分けられなかったときの受け皿」であって、
  分けられるようにする話ではない。両方要るが、切り分ける
- 種類の自動マージ（本物の二重記録を機械が勝手に片付ける）はしない。G18 のとおり
  「どちらを残すか」は人の裁定

## 5. 検証

- 決定論の判定（D1）: 同じキー・項目が重なる/分かれる の両方でユニットテスト
- D3 の適用: 提案ブロックの JSON から骨格が変わることをテスト（LLM 0）
- **実データ e2e**: この XRD カードを一周し、カードと結晶に分けても**警告が出ない**こと、
  分けた結果ピークから結晶への参照が張られること（`ensure_same_source_links` の
  containment 経路）を確認する
