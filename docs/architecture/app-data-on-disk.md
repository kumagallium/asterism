# ADR: デスクトップは手元のディスクに保存する — チャットと設定をブラウザから出す

- **状態**: 実装中（branch `feat/desktop-appdata-on-disk`・2026-08-18）
- **決定者**: kumagallium + Claude Code
- **起点**: ユーザー指摘「Asterism のチャット欄に『このブラウザ内に保存』とある。
  デスクトップアプリにそれが書いてある違和感がある。デスクトップアプリなら
  Graphium のように PC のストレージに保存されるのはどうか」。

## 問題

Ask のチャット履歴は `localStorage['asterism.ask.threads.v1']` にある
（ADR `ask-chat-threads.md` D2）。デスクトップ版は同じ SPA を Tauri の窓で
動かしているだけなので、**チャットは Tauri の WebView の localStorage に入る**。
UI の「（このブラウザ内に保存）」は正直な表示で、中身も本当にブラウザ内だった。

同じことが Ask だけでなく起きている。`localStorage` にあるもの:

| キー | 中身 |
|---|---|
| `asterism.ask.threads.v1` | チャット履歴（60 スレッド・約 5 MB 上限） |
| `asterism.models` | モデル定義と選択中モデル |
| `asterism.keys` / `asterism.keyRemember` | API キー（`sessionStorage` との選択制） |
| `asterism.lang` | 表示言語 |
| `asterism.usdJpy` | 使用量画面の為替レート |
| `asterism.workbench.tier` | かんたん / 詳細 |

表示の違和感だけではなく実害がある:

1. WebView のデータはアプリの再インストールや WebView データ消去で**消える**。
   Time Machine 等のバックアップにも乗りにくい。
2. データセット・グラフは PC のディスク（`~/Library/Application Support/Asterism`）に
   あるのに、**チャットと設定だけ別の場所**にある。ユーザーに説明できない。
3. 60 スレッド / 5 MB の上限（超過時は古い半分を捨てる）は localStorage 由来で、
   ディスクなら本来不要な制約。
4. 同期フォルダに置いてデバイス間で持ち回れない。Graphium はできる。

「ブラウザにしか置けない」はプラットフォームの制約ではない。**デスクトップでは
サーバ＝自分のディスク**であり、その口はすでに開いている
（ADR `source-staging.md` と同じ構図）。

## 決定

### D1. 分岐は `isTauri()` ではなく「サーバが単一ユーザーか」

保存先は**接続先のサーバの性質**で決める。UI が Tauri の中にいるかどうかではない。

| 接続先 | チャット・設定の置き場 |
|---|---|
| `asterism-local`（デスクトップ／手元起動） | **PC のディスク** `<home>/appdata/` |
| 共有 api（`asterism.e4m.jp` / docker） | `localStorage` のまま |

- 共有 api に置いてはいけない理由は ADR `ask-chat-threads.md` D2 のまま生きている
  ＝本番は**一つの合言葉を全員で共有する**ログイン形態で、ユーザー識別が無い。
  サーバ保存＝全員の質問が全員に見える。
- 逆に `asterism-local` は**ループバックのみ・単一ユーザー**で、書き込みトークンは
  サーバ側で自動注入される（`local.py` の loopback token injection）。ここに置くのは
  安全であり、それが自然。
- `isTauri()` で分けると、手元で `asterism-local` を起動してブラウザで見ている人が
  恩恵を受けられず、逆にデスクトップ版から共有サーバに繋いだ場合に**他人に見える**
  場所へ書いてしまう。**サーバに申告させる**のが正しい境界。
- 申告は `GET /api/appdata/info` → `{"single_user": bool, "home": str|null}`。
  単一ユーザーでないときは `info` 以外のすべてが 404（共有 api の挙動は不変）。

### D2. ディスク上の形＝1 会話 1 ファイル（Graphium と同じ）

```
<home>/appdata/ask/<uuid>.json   ← 1 スレッド＝1 ファイル
<home>/appdata/settings.json     ← モデル定義・言語・タブ・為替
```

- Graphium の `appdata/asset-chats:<uuid>.json` と同じ発想。**人がフォルダを開いて
  見て分かる**形にする（不透明な DB に押し込まない）。
- 1 ファイル 1 会話なので**変更したスレッドだけ書く**（全体を毎回書き直さない）。
  ディスクに移す動機の一つが上限の撤廃なので、全体シリアライズは採らない。
- 書き込みは tmp → `os.replace` の原子的差し替え・0600。壊れたファイルが 1 つ
  あっても他は読める（1 件の破損で全滅させない）。
- id は uuid4 の厳密検証。`_staging` と同じ「path になり得ない capability」。

### D3. API キーはディスクに書かない

- Graphium の `server-data/models.json` にも API キーは入っていない（`provider` /
  `modelId` / `apiBase` のみ）。同じ扱いにする。
- キーは今のまま `localStorage`（記憶する）/ `sessionStorage`（タブを閉じたら消す）
  の選択制。**設定のうちキーだけがブラウザに残る**。
- クライアントの取り違えに備え、**サーバ側でも防ぐ**: `settings.json` へ書く前に
  キー名に `key` / `token` / `secret` / `password` を含む項目を落とす。

### D4. 保存先は 1 つ。既定は `~/Documents/Asterism`、設定画面から変えられる

- 保存先は `ASTERISM_LOCAL_HOME`（データホーム）**1 つに統一**する。チャットも設定も
  データセットもグラフもその下。保存先が 2 つあると「どっちに何があるか」を
  ユーザーに説明できなくなる。
- **既定は `~/Documents/Asterism`**。姉妹アプリ Graphium が `~/Documents/Graphium` を
  既定にしており、Finder から見えて研究データとして扱える場所に揃える。OS の
  アプリデータ領域（macOS `~/Library/Application Support`）は、普段は目に入らない。
- **既存ユーザーのデータは動かさない**: 旧既定にデータがあれば**そちらを使い続ける**
  （移動もコピーもしない）。新規インストールだけが Documents に出る。データを
  自動でコピーする案は採らない — 数百 MB のグラフストアを黙って移す方が、
  場所が 2 通りある状態より危ない。移したい人は設定画面から変えて手でコピーする。
- 設定に「ストレージ」タブを足し、Graphium と同じく現在の場所の表示と「変更…」を置く。
  選んだパスは Tauri 側に永続化し、次回起動時にサイドカーへ `--data-dir` で渡す
  （反映には再起動が要る＝Graphium と同じ）。
- 警告を 2 つ出す:
  1. 「既存のデータは自動では移動されません」（Graphium と同じ文面）
  2. **同期フォルダ（Dropbox / Google Drive / OneDrive / iCloud）を選んだとき**、
     Oxigraph のストアは同期と相性が悪く壊れ得る旨。Graphium が同期フォルダを
     勧められるのは中身が JSON / Markdown だけだからで、Asterism はバイナリの
     グラフストアを抱えている。**同じ勧め方をそのまま真似ない**。

### D5. 移行は 1 回だけ、静かに

- 単一ユーザーモードで初回に接続したとき、**サーバ側が空**かつ `localStorage` に
  スレッド／設定があれば、それをディスクへ引き上げてから `localStorage` の該当キーを
  消す（二重管理を残さない）。API キーは対象外（D3）。
- 失敗したら何もしない（localStorage をそのまま残す）。移行は成功したときだけ確定する。
- **例外＝最初の描画に効く 2 つ**（表示言語 `asterism.lang`・かんたん/詳細
  `asterism.workbench.tier`）は、移行後も `localStorage` に**キャッシュとして残す**。
  サーバが正だが、消すと毎回「既定で描画 → サーバの値が届いて切り替わる」の
  ちらつきが出る。起動は localStorage の値で描き、サーバの値が違えば合わせる。
- 「いま使われている場所」と「次回から使う場所」は別物になり得る（D4 の保存先変更は
  再起動で反映）。設定画面は両方を見せ、食い違っているときは再起動を促す。

### D6. 秘密はサーバ側でも落とす — ただし名前で消しすぎない

- `settings.json` に書く前に、**ネストした位置も含めて**秘密らしいキーを落とす
  （実データが `{"models": {"models": [{"apiKey": ...}]}}` というネスト構造なので、
  トップレベルだけの防御は素通しになる）。
- 判定は部分一致（`apikey` / `api_key` / `token` / `secret` / `password` / `passwd` /
  `credential`）＋完全一致 `key`。`apiBase` / `activeModelId` / `sortKey` のような
  正当なフィールドは残す。**名前だけを頼りに消しすぎると「設定が黙って保存されない」
  という分かりにくい壊れ方になる**ため、単独の `key` は部分一致に含めない。
- 落とした件数だけをログに出す。値は出さない。

### D7. `appdata/` の中身は人が触ってよい

- 1 会話 1 ファイルの JSON にした狙いは「開いて分かる」こと（D2）。したがって
  ユーザーがファイルを手で消す・コピーする・シンボリックリンクを張ることは
  **想定内**として扱い、サーバ側で締め出さない。単一ユーザーの、自分のディスクの、
  自分のファイルである。
- 代わりに壊れ方に強くする: 壊れた JSON は**その 1 件だけ**を飛ばす、書き込みは
  tmp → `os.replace` の原子的差し替え、スレッド数の上限は **uuid4 形式のファイルだけ**
  を数える（同期フォルダが作る "(conflicted copy)" 等の混入で上限を誤らない）。

### D8. 表示は実態を言う

- ディスク保存のとき: 「（この PC に保存）」＋設定のストレージタブで実際の場所を表示。
- 共有ブラウザのとき: 「（このブラウザ内に保存）」のまま——そちらでは事実だから。

### D9. 引っ越しは「起動時、サイドカーを立てる前」だけ

保存先を変えても中身は移らず、手でコピーしてもらっていた（Graphium と同じ）。
データが育つほどこれは重くなるので、「移す」で済むようにする。

- **動かせる瞬間は 1 つしかない**: アプリが動いている間は Oxigraph が store を
  掴んでいる。稼働中にコピーすれば、書かれている最中のファイルを掴んで不整合になる。
  唯一安全なのは `boot()` の中、**サイドカーを起動する前**。だから「変更…」は
  予約だけを置き、実際の移動は次の起動時に行う（反映が再起動なのと同じ理由）。
- **同じディスクなら移動、違うディスクならコピー**: `rename` が通ればアトミックに
  一瞬で終わる。通らない（別ボリューム）ときは再帰コピーし、**旧フォルダは消さない**。
  容量を二重に食っても、消してから失敗するより良い。残ったことは画面で伝えて、
  ユーザーが自分で消せるようにする。
- **失敗したらデータを失わない方に倒す**: 移行に失敗したら上書き設定を**取り消して**、
  旧の場所で起動する。書きかけの移行先は消す。「起動しなくなる」「両方が中途半端」を
  作らない。
- **移行先が空でなければ移さない**。既にデータがある場所へ流し込むと、どちらの
  データも信用できなくなる。その場合は「その場所にあるデータを使う」だけにする。
- **待たせる間は黙らない**: 数百 MB のコピーは数十秒かかる。移行中はスプラッシュ窓を
  出す（通常の起動では窓はサイドカーが ready になってから作られるので、そのままだと
  無反応に見える）。
- **結果は次に画面を開いたときに伝える**: とくに「コピーしたので旧フォルダが残っている」
  ことは、言わなければ気づけない。

## 却下した案

- **Tauri の fs プラグインで SPA から直接ファイルを書く**: 窓はリモートの
  ループバック URL を読んでおり、capability は「updater と relaunch の IPC だけ」に
  絞ってある（PR #377）。fs まで開けるのはセキュリティの後退で、しかもブラウザ版と
  2 実装になる。サーバ経由なら 1 実装で両方成立する。
- **既存ユーザーも `~/Documents/Asterism` へ移す（初回起動でコピー）**: 全員の場所が
  揃うが、数百 MB のグラフストアを起動時に黙ってコピーし、途中で失敗すれば壊れる。
  旧既定にデータがあればそこを使い続ける方が安全で、しかも「何も起きない」。
- **2 段構え（重いデータは固定、軽いアプリデータだけ別フォルダ）**: 同期事故は
  原理的に防げるが、保存先が 2 つに割れる。D4 の理由で採らない。
- **共有 api にも appdata を載せる**: ADR `ask-chat-threads.md` D2 の理由がそのまま。
  ユーザー識別が入る日まで載せない。
- **スレッド全体を 1 ファイルにする**: 実装は単純だが、1 文字の変更で全会話を
  書き直すことになる。上限撤廃と噛み合わない。
- **稼働中にデータを引っ越す**: 進捗を見せやすいが、Oxigraph が書いている最中の
  store を掴むことになる。壊れ方が最悪（気づくのが後）。
- **コピーが終わったら旧フォルダを消す**: 容量は節約できるが、消した後に新しい方の
  異常が見つかったとき戻れない。残す。

## 残タスク

- Windows / Linux でのデータホーム変更の実機確認（macOS で一周したあと）。
- 移行の進捗（バイト数・残り時間）。いまは「移しています」だけで、完了までの
  見当がつかない。
- 移行前の空き容量チェック（いまは足りなければコピーが失敗し、旧を残して復帰する）。
