# ADR: 前面 UI を「1 件／絞り込み × カード」に作り替える（object cards）

- **状態**: 実装中（branch `feat/object-cards-ui`、PR A = ADR＋契約層、2026-09-23）
- **決定者**: kumagallium + Claude Code
- **背景**:
  - 津田先生の指摘: チャットだと成果物がわかりにくい。持ち出せて単体で動くもの
    （standalone）を出すべき。「これからは one software per object の時代」。後に
    「python である必要はない。ローカル LLM ベースのエージェントを生成できればよい」。
  - 熊谷さんの現状認識: 作る UI が本当は大事だが、多くのユーザーは使う UI しか見ない。
    使う UI で既存チャット（Claude 等）に体験で勝てないので、**勝負する場所を会話から
    成果物に移す**。
  - Asterism にしか出せない成果物 = **出典と版が付いたまま梱包されたもの**
    （カード・エージェント）。他の AI が吐く使い捨てスクリプトとの差は中身のデータ。
  - **Asterism は汎用基盤**（材料科学前提ではない）。Starrydata は上に載る 1 データ
    セット。論文（文書層）も装置ファイルも同じ仕組みで載る。設計に分野固有の名詞を
    書かない（引き継ぎ書 §7）。

## 問題

引き継ぎ書の設計を見直した際に見つかった穴。反映先は本 ADR および実装ステップ。

| # | 穴 | 反映先 |
|---|---|---|

| 2 | 現行ツールの出口は「列名の集合」で意味型ではない | Step 2 |
| 3 | staging（TTL 7 日）では「自分のデータ」が消える → 私の棚に永続化 | Step 4 |
| 4 | 運営者の「作る UI」は残る（同居） | Step 5 |

| 6 | 試作の設計に材料科学が混ざっていた（既定カードの名前・絞り込みの項目・近さの尺度） | 決定 7・8・16 |
| 7 | 出口の意味型が数値系だけで、手順・階層・網目（構造）を見ていない | 決定 7・15、§5.1 |

## 決定

### O1. 三層

**固い核**（事実・出典・版・意味空間・1 件の同一性 = 全員共通、作らせない）／**契約**
（ツールの入口と出口の型を意味空間の語彙で書く = 機械が検査）／**柔らかい殻**（計算の
中身と見せ方 = その場で作る・人がいじれる）

### O2. 蓄積と使い捨て

棚（事実・ツール・意味の対応づけ）は蓄積。タスク記述・組み合わせ・生成物（カード・
エージェント）は使い捨て = **作り直せる**。生成物を保管する設計にしない

### O3. ページの単位

**1 件**（個体。IRI を持つ）と **絞り込み**（条件で決まる一覧。IRI を持たない。既定の
条件は決定論の問い合わせ）。「ある物性が高い材料の一覧」「自分のファイルの全件」は
絞り込み

### O4. 左の一覧

2 セクション: **自分のデータ**（置いたファイルに出てきた 1 件と、そのファイル全体の
絞り込み。全部並ぶ）／**オープンデータ**（さがして開いた 1 件・絞り込みが残る。一覧
化しない）。= 私の棚／公開の棚（既存 local-first 3 層に名前を付けたもの）

### O5. 型の一致で分かれる

置いたファイルの**形**が既存の型と一致 → 設計なしで置ける（1 件の照合だけ）。部分一致
→ 一致した列だけで置き、残りは後で「定義を直す」。**一致なし → 「棚を作る」へ渡し、
型ができたら戻る**。判定は列名・単位・方言の検出で決定論

### O6. 2 つの「型」

**入力の形**（ファイルの型: 設計が要るかを決める）と **1 件の種類**（クラス: 既定
カード・絞り込みフォーム・並びの共通化の単位）。新しい形でも既存の種類に落ちれば
カードは最初から出る

### O7. 既定カードの決めかた

**分野で決めず、データの形で決める。** `facts`（棚にあること）と `breakdown`（出典の
内訳）は必ず。`series`（条件→量）は条件つきの量があるときだけ。`ranked`（近いもの＝
共有するキーやつながりで測る）はつながりがあるときだけ。`flow`（作られた手順）は
provenance があるときだけ。**名前はスキーマから来る**

### O8. 絞り込みのフォーム

「1 件の種類」のスキーマから**自動生成**（どの量・どの分類・どの条件・どの並べ方が
あるか）。LLM ゼロ。「1 行書く→条件に直す」は Phase 2

### O9. 見せ方の 3 段

**選ぶ**（型から決まった既定ビューを別のビューに差し替える）／**組む**（軸・色分け・
しきい値・並び）／**書く**（LLM が仕様を書く = Phase 2、印が付く）。書く対象は Python
ではなく **Vega-Lite／Mermaid（flowchart 部分集合）／表仕様**

### O10. 描画は house style

3 つの仕様は Asterism の見た目で描く。Vega-Lite は config テーマ（色・フォント・軸）、
グラフは **Mermaid を解析して React Flow で描く**（Mermaid 自身の SVG は使わない。
見た目が合わない）、表は自前の描画器

### O11. 生成コードを実行しない

仕様（JSON／Mermaid テキスト）はデータ。描画器は固定。`CLAUDE.md` の不変条件と両立
させる唯一の形

### O12. 持ち帰る単位

**ページのエージェント**（`facts/` `tools/` `cards/` `AGENT.md` `mcp.json`
`materials.json`）。エージェントは**答えを作らず、ツールを選ぶだけ**（既存 Ask と
同じ規律）→ 数字に出典が付いたまま。範囲が狭いのでローカル LLM で足りる。カード単位
の `.py` は副産物で Phase 1 では作らない

### O13. 配れる判定

`配れる = 自分のデータを材料に含まない ∧ 全材料が再配布可`。材料表から機械が決める。
判定不能は「手元限り」に倒す。エージェント書き出しは「配れる版（自分のデータを抜く）」
を選べる

### O14. 2 つのロールの同居

右上の切り替え「使う／棚を作る」で**同じ画面に同居**（別アプリにしない）。「データを
置く」は**同じかんたんウィザード**（聞く数を最小にし、ページで終わる）。「棚を作る」
は新しい形のときと、公開品質まで詰めるときの入口。利用者は材料表の「定義を直す」から
だけ厚い版に入る

### O15. flow の入れかた

Phase 1 は**既存の取り込み由来（provenance）だけで flow を描く**。MatPROV 等の
実験手順データは後で同じ描画に載せる

### O16. 汎用性

画面に出る名詞（1 件の種類・量・条件）は**すべてスキーマから来る**。コード・設計・
テスト名に分野固有の名詞（例: 材料・組成・温度・ZT）を書かない。テストデータは
2 分野以上で持つ

### O17. 出口の意味型（`OutputKind`）

| 値 | 意味 | 既定ビュー | Phase 1 |
|---|---|---|---|
| `quantity` | 量 1 つ＋単位（＋条件） | 数値カード | ○ |
| `series` | 条件 → 量の系列 | 折れ線（Vega-Lite） | ○ |
| `pairs` | 量 vs 量 | 散布図（Vega-Lite） | ○ |
| `ranked` | 1 件の集合＋量 | 順位表（表仕様） | ○ |
| `breakdown` | 分類ラベル＋件数 | 内訳バー（Vega-Lite） | ○ |
| `facts` | 事実の集合そのもの | 出典つき表（表仕様） | ○ |
| `flow` | 工程の連なり（PROV の activity/entity の有向グラフ） | グラフ（React Flow） | ○（provenance からのみ） |
| `timeline` / `tree` / `network` / `statement` | 時間順／部分と全体／網目／出典つきの文 | — | 後（逃げ道の印が溜まった形から） |

ツール宣言に `output_kind` と、`quantity`/`series`/`pairs` は `quantity_kind`
（QUDT）・`unit` を必須で付ける。無いツールは `facts`（後方互換）。
（本実装での扱いは O25 参照 — `quantity_kind`/`unit` は任意に緩めた。）

### O18. ビュー仕様（`ViewSpec`）— 3 言語、いずれも**データであって実行しない**

```yaml
lang: vega-lite | graph | table
spec: {…}            # 下の 3 つのどれか
custom: false        # true = 「書く」で LLM が書いた（印が付く・Phase 2）
```

| lang | 中身 | 描画器 |
|---|---|---|
| `vega-lite` | Vega-Lite の JSON。Asterism の config テーマ（`ui-guidelines` の色・フォント・軸）を必ず合成 | vega-embed |
| `graph` | `{nodes:[{id,label,kind: entity\|activity\|other, props}], edges:[{from,to,label?}]}`。**Mermaid flowchart（`graph LR/TD` の部分集合）から決定論で変換**して得る。逆変換（graph → Mermaid）も持ち、持ち帰り束では Mermaid テキストとして残す | React Flow（house style・決定論の並べかた） |
| `table` | `{columns:[{field,label,unit?,format?}], sort?, group_by?, limit?, highlight?:[{when,style}]}` | 自前（既存の表の部品） |

既定カードも同じ 3 言語の仕様を**決定論で生成**する（= 描画器は 1 系統。「書く」で
LLM が書くものと同じ形）。

### O19. カード仕様（`CardSpec`・私の棚に保存）

```yaml
id: card-…                  # 決定論（subject + tool + params のハッシュ）
subject: {kind: individual, iri: …} | {kind: set, set_id: …}
tool: <registry tool id>
params: {…}
view: <ViewSpec>
materials:                  # Step 6 で機械が埋める
  - kind: own | open
    dataset: <dataset id>
    snapshot: <version>
    license: <SPDX or "unknown">
    count: <int>
shareable: <bool>           # 派生。own が無い ∧ 全 license が再配布可
```

### O20. 左の一覧の項目（`SubjectItem`）

```json
{ "kind": "individual" | "set", "id": "<IRI or set_id>", "label": "…", "class_label": "…",
  "source": "own" | "open", "card_count": 4, "match": "linked" | "ambiguous" | "own_only" | null }
```

`source: own` は「データを置く」から、`open` は「さがす」から生まれる。ラベルは
K4（生の識別子を見せない）。

### O21. 絞り込み仕様（`SetSpec`・IRI を持たない）

```yaml
set_id: set-…                    # 決定論（class + where + order のハッシュ）
class: <1 件の種類の IRI>
where:
  - {property: <IRI>, op: gt|lt|eq|between|in, value: …, at: {property: <条件の IRI>, value: …, tolerance: …}?}
order_by: {property: <IRI>, dir: desc|asc, at: {…}?}
limit: 20
source_scope: all | own | open   # 自分のファイル全件 = own
```

フォームの項目は `class` のスキーマから生成する（量の種類・分類・条件になりうる量・
並べ方）。**分野の項目を固定で書かない**。

### O22. 形の一致（`ShapeMatch`）

```json
{ "type_id": "<既存の型 or null>", "dialect": "…", "matched_columns": [...], "unmatched_columns": [...], "confidence": 0.0 }
```

`type_id` あり → 置ける（部分一致は `unmatched_columns` を後回し）。null → 「棚を作る」
へファイルごと渡し、型ができたら「置く」に戻る。

### O23. エージェント束（standalone）

```
<subject-slug>/
  AGENT.md         # 何のエージェントか・答えられること・答えられないこと・出典の出しかた（答えを作らずツールを選ぶ）
  mcp.json         # ローカル LLM や AI クライアントに貼る設定（同梱 stdio を facts/ と tools/ で起動）
  facts/           # 使った事実の切り出し（Turtle or Parquet）。値ごとに IRI・出典・snapshot。全 DB ではない
  tools/           # このページに効くツールの宣言（registry の部分集合）
  cards/           # いま並んでいるカード（CardSpec + ViewSpec。graph は Mermaid テキストで）
  materials.json   # 材料表と shareable
```

**Asterism への HTTP 依存を持たない。** 実行系は既存の stdio MCP をそのまま束に向ける
（`asterism-agent serve <dir>` のような 1 コマンド）。

### O24. YAML の形と役割の規則

`query_tools.yaml` の各ツールに `output_kind`（省略時 `facts`）と、`result.item` の
各列に `role`（および任意で `quantity_kind`/`unit`）を**任意で**足せるようにする。
`output_kind` の語彙は定数 `OUTPUT_KINDS`（`quantity` `series` `pairs` `ranked`
`breakdown` `facts` `flow`）。`flow` は宣言できない（O28）。`role` の語彙は定数
`ITEM_ROLES`（`subject` `label` `value` `x` `y` `series` `category` `count` `at`）。
`output_kind` ごとに必須・任意の role を定数 `ROLE_RULES` で定める:

| output_kind | required（各ちょうど 1 つ） | optional |
|---|---|---|
| quantity | value | subject, label, at |
| series | x, y | series, subject, label |
| pairs | x, y | subject, label |
| ranked | subject, value | label, at |
| breakdown | category, count | — |
| facts | — | どれでも |

`output_kind` を**明示した**ツールだけこの規則を検査する（違反は保存/parse 時に
error）。省略（= facts）は検査しない。同じ role が 2 列に付くのも error（facts の
optional は除く）。

### O25. `quantity_kind`/`unit` を任意にした（引き継ぎ書からの逸脱）

引き継ぎ書 §5.1 は「`quantity`/`series`/`pairs` では `quantity_kind`/`unit` を必須」
としているが、単位がパラメータで決まるツール（例: 同梱の `property_ranking` は
`property_y` 引数で量が変わる）が実在するため、本実装では**任意**とし、lint が
warning を出すに留める。値の検証（QUDT カタログに存在するか）も Phase 1 ではしない
（文字列を素通しする）。`series` の `x` は年や日付などの座標であることが多く物理量の
単位を持たないため、warning の対象からも外す（`y` のみを見る）。

### O26. 推定規則（`infer_output_kind`）

`output_kind` の無い宣言から `(kind, {item_key: role})` を推定する、純粋・決定論・
store アクセスなしの関数を設ける。**列名の意味は見ない**（分野語を持ち込まない）。
`number: true` の指定・query の構文・`_iri` 接尾だけで決める。この順で最初に当たった
ものを採る:

1. 数値列がちょうど 1 つ ∧ その var が query 内で `(COUNT(` … `AS ?var)` の AS 先
   ∧ 数値でない列がちょうど 1 つ → `breakdown`（category = その列, count = 数値列）
2. 数値列がちょうど 1 つ ∧ query が `LIMIT 1` で終わる（末尾の空白・改行は無視、
   大文字小文字無視） → `quantity`（value = 数値列, subject = 最初の IRI 列があれば）
3. 数値列がちょうど 1 つ ∧ query に `ORDER BY DESC(?var)` か `ORDER BY ASC(?var)`
   があり var がその数値列の var ∧ IRI 列が 1 つ以上 → `ranked`（subject = 最初の
   IRI 列, value = 数値列）
4. それ以外 → `facts`（roles 空）

規則 3 は `ORDER BY ?var`（括弧なし）には当てない。**数値列が 2 つ以上は必ず
facts**（判断が要るものは保守側に倒す）。

### O27. 推定は読み出し時に付け、YAML は書き換えない

`annotate_output_kind` は生 dict のコピーを返す関数で、`output_kind` が既にあれば
そのまま + `output_kind_inferred=False` を付け、無ければ `infer_output_kind` の結果
を `output_kind` に入れ、`result.item` の各 spec に role を足し（短縮形 `str` は
`{var, number: False, role}` の dict に展開）、`output_kind_inferred=True` を付ける。
保存されている YAML 自体は変更しない。API の読み出し経路（一覧・単体）がこの関数を
通す。

### O28. `flow` は宣言できず provenance からのみ

`flow` は `DECLARABLE_OUTPUT_KINDS`（`OUTPUT_KINDS` から `flow` を除いた集合）の外
にあるため、ツール宣言の `output_kind` に書くと parse で error になる。`flow` の
材料は宣言ツールではなく `prov_graph`（O29）が provenance から都度組み立てる。

### O29. `prov_graph` の 7 述語と向きの正規化・kind・label・出どころ

汎用の有向グラフ探索を新設する（既存 `provenance_of` は特定データセットの述語を
直書きした線形 chain で汎用ではない。O30 のとおり据え置く）。辿る述語
（`prov:` = `http://www.w3.org/ns/prov#`）と**辺の向きの正規化**（from が先・to が
後 = データ／時間の流れ。描画器に PROV の知識を持ち込まないため、ここで揃える）:

| 三つ組 | edge |
|---|---|
| `?e prov:wasGeneratedBy ?a` | a → e, `generated` |
| `?a prov:used ?e` | e → a, `used` |
| `?e2 prov:wasDerivedFrom ?e1` | e1 → e2, `derived` |
| `?e prov:wasAttributedTo ?ag` | ag → e, `attributed` |
| `?a prov:wasAssociatedWith ?ag` | ag → a, `associated` |
| `?a2 prov:wasInformedBy ?a1` | a1 → a2, `informed` |
| `?e prov:wasQuotedFrom ?src` | src → e, `quoted` |

探索は起点 IRI の**系譜**（上流全部＋起点の下流 1 hop）に限る。同じ activity の
他の出力は辿らない（実機で 1 activity が数百件の実体を生成するとき、両方向 BFS
だと起点の系譜に辿り着く前に無関係な兄弟の壁で `max_nodes` を使い切ってしまうた
め）。上流（起点から離れる向き。`max_depth` 段まで）は起点から実体側の 4 述語
（`wasGeneratedBy`/`wasDerivedFrom`/`wasAttributedTo`/`wasQuotedFrom`）と
activity 側の 3 述語（`used`/`wasAssociatedWith`/`wasInformedBy`）を**主語役の
み**で繰り返し辿る。下流（起点を使ったもの）は起点自身から
`wasDerivedFrom`/`used`/`wasQuotedFrom` で**目的語役として起点を指すものだけ**
1 hop 辿り、そこから先へは展開しない。`max_nodes` 個まで（超えたら
`graph.truncated: true`）。1 段ごとに 1 回の SPARQL（`VALUES ?n { ... }` で前段の
節をまとめて問う）。

**kind** の決めかた（型 IRI から。分野語なし）: `a prov:Activity` があるか、型 IRI
のローカル名が `Activity` で終わる → `activity`。`a prov:Agent`（または
`prov:Person`/`prov:Organization`/`prov:SoftwareAgent`）→ `other`。それ以外
（`prov:Entity` 含む・型不明含む）→ `entity`。

**label** の決めかた: `rdfs:label` → `schema:name`（`http://schema.org/name` と
`https://schema.org/name` の両方）→ `dcterms:title` → 型 IRI のローカル名 → IRI の
ローカル名（`#` か `/` の後ろ）。**生の IRI を label にしない**（K4）。言語タグ付き
が複数あれば `ja` → `en` → 最初。

**出どころ**: 版グラフの `GRAPH ?g` を束縛して `dataset_id_of_canonical_graph(g)` で
`dataset_id` を、`/v{n}` の末尾から `snapshot`（`"v3"` の形）を取る。版グラフの一覧
は `canonical_graphs(client)` から、`ast:liveGraph` で解決した版グラフだけに絞る
（FROM 束では `?g` が取れないので `FROM NAMED` + `GRAPH ?g { ... }` を使う）。
`materials` = `graph.nodes` に現れた `(dataset_id, snapshot)` の重複なしの一覧
（並びは dataset_id, snapshot の辞書順）。`found` = 起点 IRI が少なくとも 1 つの

### O43. 「グラフを足す」は見せ方を先に選ぶ（項目×集計だけの案は却下、PR F4、2026-09-24）

「項目を選ぶ→集計を選ぶ」という素直な 2 問フォームでは、横軸（例えば年）を選ぶ場所が

見せ方ごとに要る項目の数・種類（quantity/category/label）が違うため、先に形を固定
しないと「聞くべき項目」自体が決まらない。O17（出口の意味型）の型（series/ranked/
breakdown/pairs/quantity/facts）とそのまま対応させ、②で選んだ項目から出口の型が
一意に決まる。フォームは既存の「＋ 条件で集める」と同じくモーダルにしない
（O40・K17: 1 工程 1 画面。押した同じ画面の上部に開く）。入口は 1 件のページ・
条件で集めた一覧のページの見出しの横（O40 の「操作は常に見える」を踏襲）。

「言葉で頼む（自然文から LLM がグラフを組む）」は Phase 2 に送り、本 PR には出さない。
判定で見つかった罠（ボタンを押しても何も起きず離脱する）を再演しないためで、LLM の
入口はこの PR に一切無い（O11 の生成コード実行なしの方針とも整合）。

### O44. 妥当性表はサーバと UI の双方に持つ（PR F4）

見せ方 × 項目の組み合わせのうち許される形は表で決まっている（例: 「内訳」は
category のみ、「数字 1 つ」は quantity と集計の組のみ）。この表を UI だけに置くと、
UI をバイパックした API 直叩き（例えば category 列の平均を求める）が素通りしてしまう。
`measure_spec.py` に判定の純関数を置き、サーバ側の組み込みツール `set_measure` が
表の外の組み合わせを `ValueError` で拒否して api が 400 を返す。UI 側は同じ表を
先読みして選べない選択肢をそもそも出さない（両方に置くのは二重管理でなく、
「弱い入力を弾く最後の砦」と「迷わせない先回り」という別の役目のため）。

### O45. SPARQL は既存の組み立て関数だけで足す（PR F4）

`set_measure` が組む SPARQL も、既存の `set_breakdown`／`set_members` と同じ

`_label_lookup` の再利用に限る。見せ方が増えるたびに新しい文字列組み立て（＝新しい
エスケープ経路）を増やすと、version graph 限定・DISTINCT・IRI の `safe_iri` 通過と
いった既存の安全策を見せ方の数だけ再実装する羽目になり、抜けが生まれる。新しい
見せ方は「既存の組み立て関数への新しい入力の作り方」としてのみ増やす。

### O46. 1 件のページの既定条件は「この 1 件を指す種類」を実例から機械が探す（PR F4）

条件で集めた一覧のページでは「このページの条件」がそのまま既定の条件になるが、
1 件のページには絞り込みの条件が無い。ここで「この 1 件に関する記録」を集めるには、
「どの述語がこの 1 件を指すか」を先に知る必要がある。これを人に聞かず、version
graph の実例から `linking_kinds(client, iri)` が
`SELECT DISTINCT ?cls ?p WHERE { ?rec ?p <iri> ; a ?cls }` で機械的に求める（来歴の
クラスは除く）。データセットごとに語彙が違っても、宣言ではなく実データの形から
求めるので新しいデータセットにも同じ仕組みがそのまま効く（O16 の汎用性方針）。
候補が複数あるときだけ、②の前に人に種類を選ばせる（候補が 1 つなら聞かない＝
K17 の「聞かなくて済むことは聞かない」の踏襲）。1 件自身が持つ値（quantity が
1 つ）は「数字 1 つ」「表」でのみ選べる（他の見せ方は複数件の記録を要る形のため）。

### O51. 「観点」— 足したカードはそのページに残し、同じ種類の他のページには候補として出す（PR F6、2026-09-24）

まだ近いかも？」。O37〜O46 でワークスペース（cards）を「1 件／絞り込み×カード」の
使う画面として育てるあいだ、`tab === 'cards'` のときだけ左ナビの中身がまるごと
SubjectRail（データセットの木）に差し替わっていた。旧ナビ（ホーム／データ／つながり／
共通の言葉／アクティビティ／質問する）が画面から消え、戻り道は「見る」1 行しか無い
——「作る UI」と「使う UI」が別ものに見えていた、というのが実物スクショを見せたときの
指摘そのもの。

検討した 3 案:
1. **質問する（Ask）と同じ形で、ワークスペースの木を旧ナビの子ナビ（そのタブを選んだ
   ときだけ展開する入れ子）にする** — ユーザー自身が最初に挙げた案。しかし木は「デー
   タセット × 1 件・絞り込み」の選択そのもので、Ask のスレッド一覧（会話の履歴）より
   ずっと重い。左ナビの中に埋めると縦に長い入れ子ができ、逆に見失いやすい。
2. **左ナビはそのまま・ワークスペースの木は出さない（データセットのページから潜る導線
   だけにする）** — スペースは節約できるが、「同じ種類の他の対象へすぐ移る」という木の
   価値（O4）を殺す。却下。
3. **左ナビ（1 本・作る/使う）＋ワークスペースの子ナビ（第 2 列）＋本文、の 3 列。左ナビ
   はたためる** — 採用。左ナビと木を別の列として両立させ、狭い画面では左ナビをたたんで
   スペースを返す。

決定:
- 左ナビは `tab` で差し替えない。常に同じ 1 本（`navGroups.ts` の `NAV_GROUPS`）。
  見出し「作る」（ホーム／データ／つながり／共通の言葉／アクティビティ）と「使う」
  （ワークスペース／質問する）。かんたんウィザード（workbench）は今までどおりここに
  出さない——データ・ワークスペースから入る（O37 の「データセットが親」のまま）。
- ワークスペース（`tab === 'cards'`）だけ、左ナビと本文のあいだに第 2 列として
  SubjectRail（データセットの木・＋データを置く・検索・凡例）を出す。O50 の「見るの
  枠の中で開く」（`/define`・`/details`）はそのまま——この列も出たまま。
- 左ナビは「たたむ／ひろげる」ボタンで幅 220px ⇄ 56px（アイコンのみ・title/
  aria-label は残す）。状態は `localStorage`（既定は開いている）。本文の最小幅を割る
  画面幅（1100px 未満）では自動でたたむが、ユーザーが一度でも手でたたむ／ひろげるを
  押していれば（＝ localStorage に値があれば）そちらを優先し、自動判定では上書きしない。
- 「見る」は抽象的すぎる、という指摘のとおり「ワークスペース」に言い換える
  （`nav.cards` ／ `view.cards.eyebrow`）。「探す」（対象未選択時の見出し・O3/O5 系）
  や「〜を見る」という動詞（出どころを見る、見本を見る 等）はそのまま——名詞としての
  画面名だけを差し替える。

### O53. データは「作る」から入れる・ワークスペースは回答のダッシュボード（PR F8、2026-09-24）

ユーザーの言葉「使う UI 部分の『データを置く』が、作る UI の『データを追加』と何が違う
のか分からないかも。あくまでデータはデータセット側に入れて、新規の定義も追加もデータ
セットに入れる。使うは、作るで作ったデータセットの回答のダッシュボード、という構造に
なるのはどうですかね？」。O37〜O52 の間、ワークスペース（第 2 列・SubjectRail）に
「＋ データを置く」、作る側（カタログ・GalleryView）に「データを追加」と、データが
入る入口が 2 つ存在していた——判定・commit のロジック（PlaceView の「形が一致→その
まま追加／不一致→ウィザード」）は同じ 1 つなのに、見た目の入口が分かれていたため、
2 つの違いを説明できなかった。

決定:
- **データが入る入口は「作る › データセット › データを追加」の 1 つだけ**（ルート
  `#/datasets/add`。`tab: 'gallery', add: true`）。中身は PlaceView（判定・commit は
  無改修）。GalleryView の「データを追加」カード・詳細の `onAddData`・Ask/つながり
  画面の「データを追加」は全てここへ（旧: `navTo('workbench')` 直行）。
- **ワークスペースからはデータを入れない**。第 2 列の「＋ データを置く」は撤去。
  「自分のデータ」が空のときは「まだありません。作る › データセットで追加すると、
  ここに並びます」＋リンク「データセットへ」（`#/datasets`）に置き換える。初期画面
  （FirstScreen）の入口 1 も「あなたのデータを追加する」に言い換え、`#/datasets/add`
  へ送る。`#/cards/place`（旧 URL）は残すが、開いたら `#/datasets/add` に
  置き換える（replace）。
- **追加が終わったら回答へ**: PlaceView の commit（型が一致・設計なし）も、かんたん
  ウィザードの完了（`#/datasets/add` の「設定の手順へ」から入ったとき）も、そのデータ
  セットのワークスペースのページ（`#/cards/d/<id>`）に着地する——「作る → 使う」が
  一本道になる。ウィザードの完了先はこれまで通り `Route.returnTo`（App.tsx
  `onWorkbenchDone`）で決める。旧ナビの「見直す」からデータセットのページ経由で
  ウィザードに入ったとき（`returnTo` がデータセットのページを指す）の着地は変えない
  ——「ワークスペース（`#/cards`）」を `returnTo` に持つときだけ、完了した id で
  `#/cards/d/<id>` に振り替える。
- **言葉**: 「置く」を入口の名前に使わない（「データを追加」に統一）。ドラッグ＆
  ドロップの操作説明としての「ファイルを置く（ドロップする）」は PlaceView の中の
  文だけに残す。
- ワークスペースのデータセットのページ（DatasetPage・PR F2/F5/F6 の帯・この中の
  もの・使われている観点）は今までどおり——「追記する」のような入れる操作をここに
  新設しない。データを増やすのは作る側の「データを追加」（PlaceView の `datasetId`
  経路——既に棚にあるデータセットへ戻って続きを入れる既存の導線を再利用）。

### O54. 「種類 › オブジェクト › 観点」への作り替え（作る＝構造の定義とデータの追加、PR F9、2026-09-25）

ユーザーの指摘（2026-09-25、要約 5 点）:

1. 「あなたのデータを追加する」をなくすイメージでしたが、ダメなのでしょうか？
2. オープンデータと自分のデータを別にしていますが、世界の国のデータはあくまでも
   見本として入っているだけで後から消せるデータという形にはできないの？今後
   オープンデータを増やしていく訳ではない気もしましたが、違います？
3. タイトルの「探す」という言葉ですが、他のページは左ナビゲーションの言葉が
   タイトルになっているのに、ここだけワークスペースが見出しになっているのは
   分けが分かりませんでした。
4. 公開データを探すボタンが、データセットを探すのと何が違うのかが分かりません
   でした。このページの UX 設計がやはりちょっと微妙かも。
5. 左子ナビゲーションにはオブジェクトのリストが並び、オブジェクトの追加ボタンが
   あり（オープンデータかどうかの区切りはなくす）、押すと右側メイン画面に
   Asterism 内に存在するオブジェクトの一覧が出る（検索もできる）。それを選ぶと
   オブジェクトが追加される。構造としては、オブジェクトというクラスを選んで
   もらって、そのクラスの中の関数を作ってもらう流れ。ちなみに、これまで
   データセットの中にあったツールと被るので統一はできないんですっけ？
   データセットの中のツールは無くして、ワークスペースのオブジェクトごとの
   可視化（ツール）に統一するイメージ。あくまでもデータセットは構造定義で、
   ツールは使う UI 側に寄せる形。

O52〜O53 で「作る」＝データセット詳細（構造の定義）、「使う」＝ワークスペース
（回答のダッシュボード）と役割を分けたが、ワークスペースの入口には依然として
「オープンデータを探す」という別の追加動線（O4 由来）が残っており、①「データを
追加」との違いを説明できない（指摘 4）②見出し「探す」だけが左ナビの言葉と一致
しない（指摘 3）③オープン／自分の区切りが同梱の見本データセット 1 つのためだけに
存在する（指摘 2）という 3 つの穴として実物に残っていた。指摘 5 はこの 3 つを
まとめて解く構造（種類を選ぶ→その種類のオブジェクトを選ぶ）を提示しており、本
ADR ではこれを採用する。

決定:

- **作る＝構造の定義とデータの追加**（データセットの構造を決める・データを増やす。
  従来通り「作る」側）。**使う＝種類 › オブジェクト › 観点**（ワークスペースは
  この 3 段だけで完結し、データを入れる入口を持たない。O53「ワークスペースからは
  データを入れない」をそのまま維持）。
- 上位語は**「オブジェクト」**を採る。検討した他の候補（「対象」「もの」「項目」）
  のうち「対象」は O39 で既に「初見の利用者に伝わらない」と却下済み。「もの」は
  日常語すぎて「条件で集めた一覧」（1 件でないもの）まで指すと誤読されやすく、
  「項目」は表の列（property）と紛れる（Asterism では列にも「項目」を使う場面が
  ある）。「オブジェクト」は個体・一覧のどちらも指せる中立語として、左ナビの
  「オブジェクト」見出しと種類のページ・追加画面の 3 箇所で一貫して使う。
- **オープンデータと自分のデータの区切りをやめる。** 区切りの目的は本来「配れる
  判定」（O13＝own を含むかどうか）と「来歴」（O32 `meta.origin`）の 2 つで足りて
  おり、この 2 つは `own`/`open`/`unknown` の値としてカードの材料表・データセットの
  由来欄に残ればよい。左ナビでオブジェクトを 2 群に分けて並べる意味は薄く（指摘
  2・4 の混乱の元）、同梱の見本データセット（`is_demo`）が「オープンデータ」の
  唯一の中身になっていた実態とも合わない。**出どころは印（「見本」）として個々の
  オブジェクトに付くだけにし、一覧の並びそのものは種類ごとの 1 本にする。**
- **見本（`is_demo` の同梱データセット）は普通のデータセットとして扱う。** 特別な
  区画・特別な追加経路を持たず、他のデータセットと同じ「作る › データセットを
  追加」の対象であり、同じ「見直す・消す」操作で消せる（O32 の `origin` とは別の
  軸＝`is_demo` はあくまで表示の印であり、扱いの特例を増やさない）。今後オープン
  データセットを追加で増やす計画は無く、同梱の見本 1 つのために「オープンデータ」
  という専用の区画を維持するコストの方が大きいと判断した。
- **追加の入口を 1 つに畳む。** 従来「オブジェクトを検索して開く（探す）」と
  「データを追加する（作る）」は別画面だったが、実際に利用者がしたい操作は
  「Asterism に既にあるオブジェクトを選ぶ」か「新しい種類・新しいデータを増やす」
  のどちらかで、前者は今回の追加画面（`#/cards/add`）1 つに統合する。追加画面は
  種類の一覧→その種類のオブジェクト一覧（検索・条件で集める）→選んで子ナビに
  加わる、という 1 本道（O3 の「1 件」「絞り込み」の 2 種を両方この画面が生む）。
  「データを追加する」（新しい行を増やす。O53）は引き続き「作る › データセット」
  側の役目のまま――追加画面はデータを**増やさず**、既にある種類・オブジェクトを
  ワークスペースへ**選ぶ**だけの画面であることが、O53 の「ワークスペースからは
  データを入れない」との一貫性を保つ。
- **観点＝関数＝ツール。** 「種類ごとに持つグラフ・表の作り方」（O51 の「観点」＝
  カードの作り方）と、データセット詳細の「ツール」タブ（宣言ツール `query_tools.
  yaml` の一覧表示）は同じ実体を指しており、利用者に 2 つの言葉・2 つの画面を
  見せる理由がない。**データセット詳細の「ツール」タブを UI から撤去**し、種類の
  ページの「この種類の観点」（同梱＝`classSchema.tools` 由来、使用＝カードから
  逆算）に一本化する。`query_tools.yaml` はコードとしては**観点の保存形式**として
  残り（同梱ツールの宣言・MCP／Ask／エージェント束が読む一式は無改修）、
  「データセットは構造定義、ツールは使う側」という役割分担がそのまま UI の言葉に
  なる。
- **既定ルート**（`#/`）は先頭のオブジェクトのページ（無ければ追加画面）。O53 の
  「あなたのデータを追加する」を入口に持つ初期画面（FirstScreen）は指摘 1 のとおり
  撤去する――初回起動でも同梱の見本オブジェクトが既にあるため、初期画面という
  中間ページを経由させる理由がなくなった（データを増やしたい利用者は左ナビの
  「作る › データセット」からいつでも入れる）。

### O55. 一覧は「全部か一部か」を必ず言い、格子で並べる（PR F10、2026-09-25）

ユーザーの指摘（2026-09-25）: 追加画面のオブジェクトの一覧に表示数の限度が
あるのか分からない（全部出ているのか、こちらで勝手に絞られているのか）。また
単純な箇条書きで、右側の空白がもったいない。

O54 で追加画面（種類→オブジェクト一覧）に一本化したが、一覧そのものは検索欄の
下に縦 1 列の箇条書きを並べるだけで、件数の手がかりが一切無かった。利用者が
「これで全部か」を確かめる方法が無いのは、一覧という機能の前提（何を選べるかを
把握できる）を欠く。

決定:

- **一覧の上に件数を必ず出す。** 全部出ているときは「全部」であることを言葉で
  明示し、一部だけ出しているときは母数と表示数の両方を言葉で言う。検索中は
  一致件数を言う。件数が分からない・出せない、という状態を作らない。
- **縦 1 列の箇条書きをやめ、格子で並べる。** 1 件＝名前と補足 1 行・印を持つ
  カード 1 枚とし、画面幅に応じて列数が変わる格子に敷き詰める。右側の空白を
  埋めるための変更であり、見た目だけでなく「一覧の情報密度が低く見え、限度の
  有無が余計に読み取りにくい」問題とも表裏一体だった。
- **「もっと見る」で続きを取る。** 一度に全件を返すのではなく先頭のまとまりを
  出し、残りがあるときだけ「続きがある」ことと残り件数を言葉にした操作を足す。
  一覧の取得はページ送り（続きから取る）にし、二重取得・二重表示を避ける。

### O56. データを追加は直接ウィザードの① へ（近道は① の帯、PR F10、2026-09-25）

ユーザーの指摘（2026-09-25）: 今回とは別だが、データセットを新規で入れた直後に
出るこの画面は必要か？列が表示されていないしよく分からなかった。いきなり
ウィザードの「① 入れる」ではダメなのか？

「作る › データを追加」でファイルを置いた直後に出ていた中間画面（型の一致を
先に判定する画面）は、簡易な読み方しか持たないため装置ファイルのような形式で
実際の列数と異なる数字を表示することがあり（例: 実際には列として読めない形式
なのに「4 列」と出す）、利用者から見ると「列も出ていないのに数字だけ言われて
判断できない」画面になっていた。中間画面を経由する理由が薄い一方、素通しする
先のウィザードは実際にファイルの中身を正しく読む段（① ファイルを置く）を
最初から持っている。

決定:

- **「作る › データを追加」は中間画面を経由せず、かんたんウィザードの① （ファイル
  を置く段）へ直接入る。** 中間画面が担っていた「型の一致の判定」自体は要る
  機能だが、それを見せる場所を独立の画面から① の中に移す。
- **型の一致の近道は① の帯として出す。** ① でファイルを読んだ直後、既にある
  種類と同じ形だと判定できたときだけ「同じ形なので設計なしでそのまま追加
  できる」旨の帯を出し、そのまま追加するか・設計を見直すかを選べるようにする。
  一致しなければ帯を出さず、通常の①〜の流れに進む。ウィザードの各段（②以降）
  の中身そのものは変えない。
- これにより「列も出ていないのに数字だけの中間画面で立ち止まる」体験が消え、
  ファイルを置く→（一致すれば）近道の帯→（無ければ）通常のウィザード、という
  1 本の流れになる。

### O57. ページの中で AI と会話しながら観点を作り・直し・聞く（右のドロワー、画面遷移なし。PR F12、2026-09-25）

ユーザーの指摘（2026-09-25）: 「『観点を足す』がフォームになっているが、AI と
会話しつつ可視化（ツール）を作ってもらって調整するイメージだった。『韓国に
聞く』で急にチャットに画面遷移するのが微妙。AI との会話と可視化（ツール）作成
や質問がシームレスな UI にならないか」。

O51 で「観点」を導入した時点では、足す手段は O43〜O49 のフォーム（見せ方 →
項目 → 条件を選ぶだけ・決定論・LLM なし）のみで、ページ下の「〈オブジェクト名〉
に聞く」はチャット画面（`#/ask`）への画面遷移だった。フォームと会話が別の
入口に分かれ、しかも会話は別画面へ離脱するため、O9（選ぶ／組む／書く）の
「組む」を会話でこなす体験が欠けていた。

決定:

- **ページの会話は右のドロワー**。1 件・条件で集めた一覧・種類のページの下の
  入力欄に打って送ると、ページを離れずドロワーが開き、その質問がスレッドの
  1 通目になる。見た目と開き方は設計相談の「AI に相談」ドロワー
  （`ConsultDrawer`）と揃える。スレッドはオブジェクトごとに保つ。
- **AI が出すのは「観点の指定」（O43〜O49 のフォームと同じ params・presentation）
  と文章だけ。生成コードは書かせない（O11 を踏襲）。** 「聞く」ではページの
  読み取った値と並んでいるカードの結果をもとに答え、答えの根拠（どのカードの
  どの値か）を書く。「作る」では観点の指定を提案し、ドロワーの中でプレビュー
  したうえで「足す」を押すと O43〜O49 のフォームと同じ CardSpec・同じ
  `cardId`・同じ題名規則でページに並ぶ。「直す」では直前の提案を下書きとして
  持ち、続きの発話（「横軸を年に」「棒にして」）で指定を更新する。
- **AI の指定はサーバが検証してから決定論で実行する。** AI が返した指定は
  サーバ側の妥当性表（O43〜O49 と共有）で検証し、通ったものだけを O43〜O49 と
  同じ決定論の実行経路（`set_measure`）に渡す。検証を通らない指定は画面に
  出さない。この「AI は指定だけ・実行は決定論」という分担は、O11（生成コード
  を実行しない）・O18（`custom` の印で AI の関与を示す）と同じ考え方の延長で、
  会話の入口が増えても「実行されるのは検証済みの決定論の手続きだけ」という
  不変条件は変わらない。
- **AI のキーが無いときはドロワーがフォームに倒れる。** LLM は既定で使わず、
  キーが無ければドロワーは会話を始めず、代わりに O43〜O49 のフォームをその場
  （ドロワーの中）に埋め込んで見せる。キーがあってもフォームへ直接切り替え
  られる導線は残す。
- **既存の「質問する」タブと「AI に相談」ドロワーは据え置く。** 「質問する」は
  データ全体に聞く場所として残り、「AI に相談」は設計相談のドロワーとして
  変わらない。今回変わるのはページ下の入力欄（従来はチャット画面へ遷移して
  いた導線）だけで、これを画面遷移せずドロワーで完結させる。

### O58. 指定で表せない見せ方は AI が「書く」（Vega-Lite／表仕様／Mermaid の 3 言語だけ。データは差し込む・許可リスト・custom の印・弱い LLM は指定を優先。PR F13、2026-09-25）

O57 の「作る」は O43〜O49 の**観点の指定**（小さな JSON＝IR）を AI が出し、
サーバが妥当性表で検証してから決定論で実行する経路であり、これは弱い LLM
でも動く本線として残す。一方でユーザーの方針（2026-09-25）は次のとおり：
「AI に相談して仮に作ってくれるイメージ。コードは書かなくてもよいが、
JSON や Mermaid は書かせてもよいのではないか。AI 時代の入力フォームは触ら
ない前提にしたい。Asterism は AI 前提でよい。ただ弱い LLM で動いてくれる
とよい」。指定（IR）だけでは表せない見せ方（2 系列の重ね描き・注釈つき・
特殊な軸など）があり、これを埋めるために O57 の上に**書く**経路を足す。

決定:

- **AI が書けるのは 3 言語だけ**（O9 の「書く」の具体化）: Vega-Lite の
  JSON・表仕様（`tableSpec` と同じ形）・Mermaid flowchart（`mermaidFlow.ts`
  が読める部分集合）。この 3 つ以外（Python・SPARQL・任意のコード）は
  書かせない。O11（生成コードを実行しない）は変わらない——ここで「書く」
  対象は実行可能なコードではなく、確定した文法を持つ 3 つの記述言語のみ。
- **データは AI に書かせず、カードの結果を差し込む。** AI の JSON に
  `data.values` を持たせない。表示に使う行データは既存カード
  （`source_card_id`）の実行結果（`runCard` の rows）から、サーバ／UI が
  spec に差し込む。AI は見せ方（`mark`・`encoding`・列の使い方など）だけを
  書く。
- **サーバの検証は許可リスト方式。** `POST /api/cards/converse` の
  `<proposal>` に `kind: "view"` を追加で許し、Vega-Lite は既知の
  `mark`／`encoding` の値だけを通し、`data.url`・`data.format`・
  `transform` の `lookup`／`loader`・`expr`／`signal`・`usermeta` を含む
  spec は理由ごと拒否する（外部取得・任意式評価の芽を許可リストの外に
  置く）。表仕様は型で検証し、Mermaid はサーバ側でも同じ部分集合を検証
  する純関数を持つ。通らなければ O57 と同じく AI に理由を返して 1 回だけ
  直させる。
- **書かれた見せ方は `custom: true` の印がつく**（O18 の延長）。タイルと
  詳細に「AI が書いた見せ方」であることを小さく示し、束（AI に渡す一式）
  にも元のカードの結果と view を一緒に凍結して、AGENT.md にも印を書く。
  「指定を検証して決定論で実行した」ものと「AI が言語を書いて許可リストで
  検証した」ものを、見た目の上でも区別できるようにする。
- **弱い LLM は指定（O57／IR）を優先する。** 系統プロンプトは冒頭で「まず
  観点の指定で表せるか考え、表せるならそれを使う。表せないときだけ view を
  書く」と指示する。書く経路は強い LLM 向けの拡張であり、弱い LLM が指定
  だけで完走できる本線（O57）を壊さない——書く経路が使えなくても、指定の
  経路がフォームまで含めて独立に機能することが前提。

### O59. 1 件のページの「届く範囲」を近傍（上に 1 段・下に 2 段）に広げ、答えがページに無ければ観点を提案してから答える（PR F14、2026-09-25）

ユーザーの実データでの発端（2026-09-25）: ある 1 件のページで「一番大きい値
は？」と聞くと、その 1 件を**直接指す種類**（従来の `linking_kinds`＝1 段・
逆向きだけ）が空になり、AI に「作れる種類なし・答えるだけ」としか伝わらず
「分かりません」で終わった。実データの形は「1 件 → 親 ← 記録」——聞きたい
値は 1 件を直接指す記録ではなく、同じ親を持つ**兄弟**の記録に載っていた。
O57 の会話・O58 の書くは「種類が候補にあること」を前提にしており、前提が
崩れると両方とも機能しない。

決定:

- **近傍の定義: 上に 1 段・下に 2 段・4 形。** `linking_kinds` は「この 1
  件から上に 1 段（この 1 件が指す先＝親）、そこから下に 2 段（親を指す
  記録＝兄弟、兄弟を指す記録）」まで届く。従来の `direct`（この 1 件を
  直接指す記録）に加えて、`child_child`（この 1 件を指す何かを、さらに
  指す記録）・`sibling`（同じ親を持つ記録）・`sibling_child`（同じ親を
  持つ記録を、さらに指す記録）の 4 形を返す。除外（種類・PROV 名前空間・
  リテラルの親）は従来どおりに加え、**メンバー数が大きすぎる親は近傍から
  外す**（大きすぎる共有先は「同じ仲間」とは呼べない）。並びは段数の
  近い順→件数の多い順→名前の辞書順で固定し、AI にも人にも同じ順で見える
  （決定論）。
- **where はサーバが完成形で返す。消費側は組み立てない。** どの種類を
  選ぶとどの条件で記録が集まるか（`where`）は、近傍を計算したサーバが
  1 段のときも 2 段のときも完成した形で返す。フォームも会話も、返って
  きた `where` をそのまま使うだけで、IRI や述語を並べて条件式を自分で
  組み立てることはしない。**2 段の where は「経由」の形**（1 段目の条件
  の中に、もう 1 段先の条件を入れ子にする）で表し、入れ子は 1 段だけ
  （2 段より深くは作らない）。
- **答えがページに無ければ、まず観点を提案してから答える。** 会話は
  ページに載っている値と並んでいるカードの結果だけでは答えられない質問
  が来たとき、近傍の候補の種類で答えられる見込みがあれば、推測で答えず
  「この観点（例のような集計・並べ替え）を足すと答えられます」と観点を
  提案する。提案には「これは答えを出す提案である」という印を持たせ、
  ドロワーは「足す」が押されて実際にその観点の結果が出るまで待ってから、
  同じ質問にもう一度答え直す。ページにも並んでいるカードの結果にも
  近傍の候補にも根拠が見当たらないときだけ「このデータには無い」と言う。
  O57 の「AI は指定だけ・実行は決定論」という不変条件はここでも変わらず、
  観点を実際に足して結果を確定させるのは常に決定論の実行経路であり、
  会話が答えを捏造することはない。

## 却下した代替案

- **チャットを主役のまま** — 既存チャット（Claude 等）に体験で勝てない。
- **Python スクリプト書き出し** — 出典が剥がれる・実行できない。
- **Mermaid 自身の SVG で描く** — house style に合わない。
- **既定カードを分野で決める** — 汎用基盤に反する。
- **`output_kind` を result.item の列ごとに持つ** — 1 つの答えの形はツールに 1 つ。
- **既存 `provenance_of` の改修** — 特定データセットの述語直書きで汎用化しにくい。
