# 意味を先に、ID を後に — かんたんモードの順序を入れ替える

status: 提案（2026-08-28）
owner: kumagallium
関連: `kantan-mode-two-tier-ux.md`（K2 / K32-K43）、`column-ownership-and-growth.md`（G1 / G15 / G17）

## 1. きっかけ

利用者（2026-08-28）:

> そもそも ID ごとに項目を振り分ける必要はあるんですか？ 振り分けなくて良いなら、
> ここの UI はユニークな項目のリストを出すだけで良くないですか？
> ①現状 ID を決める→②意味を決める ですが、①ユニークな項目の意味を入力する→
> ②ID と項目を簡単な UI で振り分ける の方が良かったりしない？

## 2. なぜ今の順序が誤りか

**依存の向きが逆になっている。**

| | 何か | 何から決まるか |
|---|---|---|
| 項目の意味（`2theta = 回折角, deg`） | **列の性質** | データを見れば決まる。どんな設計にしても同じ |
| ID と帰属（どの値に住所を与えるか） | **設計の判断** | 人が「何を引用・照合可能にしたいか」で決める |

性質は判断の**入力**である。にもかかわらず今は判断（S4）が先にあり、性質（S6）が
後にある。実害は 2 つ:

1. **判断の材料が足りない。** ①「あとでつなぐ値をえらぶ」で人が見ているのは、
   生の列名と実値ひとつだけ。`Chemical Formula ｜ Al3 V` を見て「これは外の世界でも
   名前を持つか」を決めている。意味（`化学組成`）が先にあれば、同じ判断が容易になる。
2. **AI も材料が足りないまま骨格を書いている。** 骨格生成は列名と型しか見ていない。
   意味が先にあれば、骨格の推薦そのものが良くなる。

## 3. 決定

**順序を入れ替える。**

| | 前 | 後 |
|---|---|---|
| 3 | ID のつけかた | **項目の意味**（フラット・全列） |
| 4 | 項目の意味 | **ID のつけかた** |

### 3 になるもの（列の性質＝フラットな一覧）

- 各列の**意味**と**単位**（AI が下書き、人が直す）
- 単位の標準照合（QUDT）
- **取り込むか／取り込まないか**の判断（列ごと）

種類でグループ分けしない。**ユニークな列の一覧**が 1 枚。利用者の言うとおり、
ここに「振り分け」は要らない。

### 4 に残るもの（設計の判断）

- ①**あとでつなぐ値をえらぶ**（K32/K33。各行に**意味が併記される**）
- ②**ID がひとつずつを指しているか確かめる**（K36）
- **数の確認**（`47 行 → Crystal 1 件 …`）— これは①②の結果なので、ここが正しい置き場

### 変わらないもの

- 行の種類とカードの切り分けは**測って決まる**（値の分散）。判断ではない。
- 1 つの列が**属性として**載るのは 1 箇所だけ（G6）。同じ事実が 2 箇所にあると、
  片方だけ直したときに矛盾する。ID に使う列がリンクの材料として他の種類にも
  現れるのは別の話で、これは機械が張る（`ensure_same_source_links`）。

### 帰属は「機械が決める」ではなく「機械が薦める」（2026-08-28 改訂）

当初ここには「帰属（どの列がどの種類に載るか）は機械が決める（G17）。人には
見せない」と書いていた。**種類が 2 つのときだけ正しい**記述だった。

実 XRD カードの前置き 18 列は、いま全部 Crystal に載る。中身は 4 つに分かれる:

| 列 | 本当は何の属性か |
|---|---|
| `Name` `Chemical Formula` `Space Group` `Cell` `Volume` `Crystal System` `Z value` `Dcalc` | 結晶そのもの |
| `Radiation` `2theta range` | 測定の条件 |
| `Reference` | 文献 |
| `No` `CSD` `Quality` `Subfile` `RIR(I/Ic)` `Additional Patterns` | カード（PDF エントリ）自体 |

「ファイル全体で 1 つの値だから Crystal」は、載せ先が 1 つしか無いときの話。
種類を増やせる以上、どれに載るかは**測っても決まらない**。AI は薦めを出し、
**人が調整する**（利用者判断 2026-08-28）。

機械が決められるのは 1 つだけ — **値の分散クラスは跨げない**:

| 列の性質 | 載せられる先 |
|---|---|
| ファイル全体で 1 つの値 | カード側の種類のどれか（行の種類に載せると同じ値が全行に写る＝G6） |
| 行ごとに変わる値 | 行側の種類のどれか（カードに載せると N 個の値が 1 件に入らない） |

だから調整の選択肢は**同じ分散クラスの種類**に限る。跨ぐ選択肢は出さない —
出せば、いま G6 が防いでいる二重記録を人の手で作れてしまう。

## 4. 副次的な利得

**per-map 段が痩せる。** 今の per-map プロンプトは「列を map に束ねる」と
「意味（label）を書く」を同時にやらせており、弱いモデルは後者を落とす → だから
`generate_label_fill` の追い打ちラウンドがある（K22 の安全網）。意味が先に確定して
いれば、per-map は**束ねるだけ**になり、**labelfill ラウンドは不要になる**。

LLM 呼び出し: `skeleton → per-map ×N → labelfill ×N → document`
→ `meanings ×1 → skeleton → per-map ×N → document`（N ≧ 1 で減る）

## 5. 正直なコスト — 不可逆な判断が後ろに来る

ID は公開したら動かせない側で、意味は後から直せる側である（`pref` 恒久ルール）。
今の順序は**不可逆な判断を、注意力が一番高い最初**に置いていた。入れ替えると、
事務作業を先にやって**疲れた最後に不可逆な判断**が来る。これは実在するコスト。

緩和:
- 4 の画面は**短い**まま保つ（①はチェックリスト、②は ⚠ の付いた種類だけ）。
  意味が確定しているぶん、今より短くなる。
- 4 の入口で「ここで決めた ID は、公開すると動かせません」を 1 行言う
  （K36 の `kindNameNote` を画面頭へ昇格）。
- 公開（6）の直前に ID の一覧を再掲する案は**採らない** — 確認画面を増やすのは
  K2 の「人間ゲートは 3 つ」に反する。

## 6. データモデルの移行

いま意味は `display-meta.json` に `{predicate, label, unit}` で保存されている
（`_load_display_meta`）。**述語は設計が存在しないと生まれない**ので、このキーの
ままでは意味を設計より前に置けない。

**キーを 2 段にする（既存を壊さない）:**

| 層 | キー | 誰が書くか | いつ |
|---|---|---|---|
| 入力（新設） | `(source, column)` | 人と AI | 3 の画面 |
| 投影（既存） | `predicate` | 機械 | 設計を組むとき、列 → 述語で流し込む |

設計の各プロパティ行は必ず列を束ねているので、`(source, column) → predicate` は
決定論で引ける。**既存の `display-meta.json` は投影として残す** — 詳細モードや
再設計後の突き合わせがそのまま動く。

### 実装で決まった置き場所（2026-08-28 追記）

設計中はまだデータセットが無い（`dataset_id` が生まれるのは「ためす」の手前）ので、
入力層の置き場所は**段階で 2 つ**になる。

| いつ | 誰が持つ | どう設計に届くか |
|---|---|---|
| 設計中（3 の画面〜） | ウィザードの state | `/api/propose/continue` の `column_meanings` フォーム項目 |
| データセット作成後 | `<registry>/<id>/column-meanings.json` | `apply_column_meanings_to_document` で §9 へ投影 |

`(source, column)` を跨ぐ約束は `display-meta` と同じにした — **キーが無ければ
そのまま、空文字なら消す**。単位だけを直した操作が意味を消してはいけない。

`POST /api/design/column-meanings` は**意味を書かせる**側（LLM・ジョブ・
データセット不要）。**保管**は `GET/POST /api/datasets/{id}/column-meanings`
（決定論・書き込みゲートあり）。1 本にまとめられないのは、前者にデータセットが
無く、後者にソースが無いから。

## 7. 段階（安全に刻む）

1. **列単位の意味生成を足す**（`generate_column_meanings`）。骨格を要らない、
   per-map より簡単なプロンプト。既存経路は無改修で、まだ誰も呼ばない。 ✅ 済
2. **`(source, column)` の保管庫**と `POST /api/design/column-meanings`。
   設計を組むときに投影する経路も足す（この時点で二重に持つが、真実源は新側）。 ✅ 済
   — 置き場所は §6 の追記のとおり 2 段。投影は round-0 の組み立て直後と、
   以降**毎ラウンド**（`_overlay_column_meanings`。データの事実と同じ姿勢＝N6）。
3. **per-map の label を「まだ決まっていない列」だけに絞る**。意味が渡された列は
   per-map プロンプトで決定済みとして伝え、labelfill の対象からも外す。全列の
   意味が決まっていれば labelfill ラウンドは 0 になり、そこで LLM 回数が減る。

   > 当初は「per-map から label を外す」と書いていた。段階 4 より前に外すと、
   > 画面がまだ意味の段を呼んでいない間、設計の label が全部空になる（「途中で
   > 止めても壊れない」に反する）。渡されたぶんだけ聞かない形にすれば、段階 3
   > 単体でも今日と同じで、段階 4 が入った瞬間に labelfill が自然に消える。
   > 2026-08-28 改訂。
4. **画面を入れ替える**。S6 の②③を新しい 3 へ、①（数の確認）を 4 へ。

   実装で決めた割り振り:

   | 画面 | 何をする場所か |
   |---|---|
   | **3 項目の意味**（新設・内部 step 10） | 全列の意味・単位・取り込むか。相談ドロワーの反映先もここ |
   | **4 ID のつけかた**（S4） | つなぐ値をえらぶ・ID がひとつずつを指しているか・行 → 件の対応 |
   | **5 ためす**（S7） | 実データへの問いと答え・機械が付けた値・分け方の直し・AI への注記 |

   ### 「数の確認」（旧 S6）は畳んだ（2026-08-28・利用者判断）

   意味の表を 3 へ移したあと、S6 に残ったのは**どれも他所にあるもの**だった:

   | 残っていたもの | 実は |
   |---|---|
   | 実測の件数 | ④ のゲートに予測が、⑤ ためす に実測が既にある |
   | ② 取り込むかどうか | 3 で答えてある。二度聞いていた |
   | 意味を直す入口 | ⑤ の「何かおかしい — 項目の意味に戻る」が同じ |

   **「取り込むか」は機械が引き継ぐ。** 3 で外さなかった列が設計に載っていなければ、
   人にもう一度聞かず、所有者の map に決定論で足す（`take_in_columns`／所有権の
   判定は G17 の verdict、ファイルに map が 1 つならその 1 つ）。意味が空でも
   取り込む — 「取り込むか」と「何と呼ぶか」は別の問いで、空欄なら項目名が列名の
   ままになるだけ（機械が意味を発明したのではない・K22）。

   S6 にしか無かった 2 つ（機械が付けた値の一覧・分け方の直しと AI への注記）は
   ⑤ ためす へ移した。カタログの「見直す」は 3 に着地する。人間ゲートは K2 の
   とおり 3 つのまま（読み方・意味・ID）で、画面が 1 つ減った。

   内部の step 番号は **1-9 を動かさず、意味の画面に 10 を与えた**。番号は画面の順序
   ではなく識別子で、保存されたスナップショット・再開の経路・「…に戻る」の全部が
   その番号で書かれているため。読む人が見る順番は `recipePos` が決める。
5. **骨格プロンプトに意味を渡す**（推薦の質を上げる）。ここは最後 — 前段が
   安定してからでないと、良くなったかを測れない。
6. **4 で帰属を調整できるようにする**（上の改訂）。①の行ごとのチェックボックスを
   「どの種類に載せるか」のセレクトに広げる。選択肢は同じ分散クラスの既存の種類
   ＋「新しい種類にする」（今のチェックと同じ操作がその 1 つになる）。ID に使われて
   いる列は動かせない（動かすと ID の作り方が変わる — そこは「ID の作り方」欄）。
   ✅ **カード側は済**（実 XRD で確認・下記）。行ごとの値の側（Peak / Hkl のあいだ）は
   まだチェックボックスのまま — そちらは種類が 1 つのことが多く、急がない。

   仕組みは新設していない: 骨格の `owns`（G15 で人が宣言する「この種類はこの列を
   持つ」）がもともとそのためのもので、UI が「新しい種類を作る」ときにしか
   使っていなかった。セレクトはその宣言を書き換えるだけ。

   実 XRD での確認（2026-08-28）— `Radiation` と `Reference` を種類にし、
   `2theta range` を Radiation に載せ替えた結果:

   ```
   crystal   : No CSD Name Chemical Formula … Additional Patterns  → radiation / reference へリンク
   radiation : Radiation 2theta range                              ← 人が載せ替えた列が入っている
   reference : Reference
   peak      : 2theta d I (hkl)                                    → crystal へリンク
   ```

   件数バンドも「Crystal 1 件 / Radiation 1 件 / Reference 1 件 / Peak 47 件」に
   その場で追従する。

   ### 「どれを種類にするか」の基準は、人にも渡す

   決めるのが人になった以上、判断の材料も人に要る。これまで基準は**骨格プロンプト
   にしか書かれていなかった**（`PROMOTE THE THINGS THE OUTSIDE WORLD ALSO NAMES`
   / `WHEN IN DOUBT, PROMOTE`）。同じことを①の畳みに置いた:

   | 問い | はいなら |
   |---|---|
   | 外の世界も同じ名前で呼ぶか（物質名・組成・空間群・X 線源・DOI・カタログ番号・装置名・人名・機関名・標準の分類コード） | 種類にする |
   | その値**そのもの**について後から何か言いたくなるか（項目のままだと自分の事実を持てない） | 種類にする |
   | 2 つ以上の種類から参照したいか（項目にすると片方にしか書けない・両方に書けば G6 違反） | 種類にする |

   このファイルの中でしか意味がない値（自由記述のメモ・ローカルな連番）と、測った
   数値そのものは項目のまま。

   **迷ったら種類にする** — 判断が非対称だから。余分な種類はこの画面で消せるが、
   足りない種類は設計をやり直さないと足せず、**公開して ID を配ったあとは動かせない**
   （公開後の ID 修正は別タスク `asterism_id_move_after_publish` の引っ越し台帳が
   要る話になる）。AI 側のプロンプトが同じ非対称性を理由に「迷ったら昇格」と
   書いているのと、根拠は 1 つ。

各段で `step0` / `api` の全テストと、実 XRD ファイルでの一周を通す。

### 段階 4 の実機一周（2026-08-28・`xrd-17961dd6.txt`）

S1 → S7 を一周し、SPARQL の答えが元ファイルと一致することを確認した。

| 見たこと | 結果 |
|---|---|
| 件数 | Peak 47 件 / Crystal 1 件（元ファイルの表は 47 行・カード 1 枚） |
| 面間隔の範囲 | 0.803 〜 4.161 Å（元ファイルの d 列の最小・最大と一致） |
| 最大強度 | 100（面間隔 2.248 Å・ミラー指数 (1,1,2)）＝ `40.07 2.248 100.0 (1,1,2)` の行 |
| LLM 呼び出し | **意味 ×1 → 骨格 ×1 → per-map ×2 → 文書 ×1 = 5 回**（labelfill 0 回） |

一周で見つけて直したもの:

- **labelfill が 1 回残っていた** — 機械が足したリンク行（列を読まない行）が
  「意味が空」に数えられていた。意味は列の性質なので、意味が決まっている設計では
  列を 1 つ読まない行（リンク・定数・複数列）は聞く対象から外す。
- **前置きの「実データの例」が生の行だった**（`No: 03-065-2664`）。読み取り確認
  （S2）は生の行を見せるのが正しいが、この画面の問いは「この値は何か」なので、
  ファイルが書いたラベルは要らない。
- **長い実データ 1 つで表が横に伸び、右端の「取り込む」が画面の外へ出ていた。**
  判断の列は常に見えていなければならない（列幅を決め打ち＋長い値を丸める）。
- **3 で外した列が「まだ取り込んでいない項目」として再び聞かれた。** サーバへの
  記録の往復を待たず、その画面の判断として即座に扱う。

## 8. 非目標

- 詳細モード（`WorkbenchView`）の順序は変えない。設計者は設計から入る。
- 意味の**多言語化**（いまは UI 言語に追従する散文だけ・`asterism_proposal_language`）。
- 公開後の ID 修正（別タスク `task_f7ca4975`）。この ADR は公開前の順序の話。

## 9. 未解決 → 決着（2026-08-28・実 XRD カードで確認）

材料: 利用者の実ファイル `xrd-17961dd6.txt`（`skip_rows=23` / `preamble=keyvalue`）。
**22 列**になる — 表本体 4 列（`2theta` `d` `I` `(hkl)`）と、前置き 18 列
（`No` `CSD` `Name` `Chemical Formula` … `Additional Patterns`）。

### ① 「取り込まない」と決めた列を 4 の①に出すか → **出さない**

取り込まない列は設計に載らないので ID にもなり得ない。「取り込まないのに選べる」
一覧は、読む人に成立しない選択肢を読ませる。見落としの心配は、3 で外すときに
その列を見ているので当たらない。

ただし 4 の頭に**1 行だけ**残す:「3 で取り込まないと決めた列が N 件あります
（戻って直す）」。既定は**取り込む**で、外すのは常に人の明示的な操作。

### ② フラットな一覧が長くならないか → **由来で分ける**（前置き / 表本体）

22 行はスクロールで読めるが、分けない理由が無い。**由来は意味を答えるときの
文脈そのもの**で、しかも決定論で取れる（`dialect.read_preamble_origins`）:

| 由来 | 何行に効くか | 意味の答え方 |
|---|---|---|
| 前置き（18 列） | ファイル全体で 1 つ | `Name: Aluminum Vanadium` ＝「この試料の名前」 |
| 表本体（4 列） | 1 行ごとに違う | `2theta` ＝「各ピークの回折角」 |

種類（クラス）で分ける案は採らない — 種類は**設計の産物**で、この画面はまだ設計を
持っていない。由来はファイルの性質なので、設計より前に言える。

## 10. 予告した形を、結果として同じ場所に出す (2026-08-29)

### Trigger
利用者評価 2026-08-28:「最終的にできるクラス図（どんなデータでも孤立ノードが発生しない
グラフになりますよね？）がやはりここにあると便利ですかね？ ずっと右くらいにグラフ描画が
あり、スクロールしても付いてくるみたいなのを今は想像していました」

④（ID のつけかた）には図を貼り付けた。ただしその段で**実線が引けるのは ID の入れ子だけ**で、
種類どうしの本当のつながりは per-map の段で決まる。①で作った種類は「その値そのものが ID」
なので必ず線が引かれるのだが、④の時点では引けない — そこは**点線「このあと機械が引きます」**で
予告してある。

予告した以上、**引かれたことを見せる場所**が要る。

### Decision
⑤（ためす）の右に、④と**同じ位置・同じ向き**で、実線の図を出す。

| 段 | 図の出どころ | 線 |
|---|---|---|
| ④ ID のつけかた | 骨格（`skeletonMermaid`） | 実線＝ID の入れ子／点線＝このあと機械が引く |
| ⑤ ためす | **保存済みの取り込みルール**（`rulesMermaid`） | 実線＝実際に引かれたリンク（述語名つき） |

⑤の図は AI が §1 に書いた散文の mermaid ではなく `GET /api/datasets/{id}/rules` から
決定論で組む。**説明ではなく事実を描く**（設計図を IR からコンパイルする方針と同じ）。

線を引く条件は「ある種類の項目の**行き先が別の種類そのもの**になっている」の 3 通りだけ:
join（親マップ参照）・同じ ID の作り方を指すテンプレート・同じ定数 IRI。値（リテラル）を
書いている項目は形ではないので描かない。種類が 1 つしか無いときは箱 1 つの絵になって
何も言わないので出さない。

### 実証（実 XRD カード）
`Peak --|of Crystal|--> Crystal`。④で点線だった予告が、同じ位置で実線になった。

### 語彙を③と揃えた
④は「この表全体 / 表全体」と言っていたが、③はすでに「① ファイル全体の値」と言っている。
**同じものを 2 つの言葉で呼んでいた**うえ、CSV 以外（装置の生ファイル・JSON・XML）では
「表」が嘘になる。④・②の帯を「ファイル全体」に統一した。

### 「行ごと」→「1 件ごと」— ただし尺度のラベルだけ
続けて利用者:「『行ごと』は変えない感じですか？」

**尺度のラベル**（ファイル全体 ⇔ ？ の対比）は直す。片方が「ファイル」もう片方が「行」だと
**枠がずれる** — ファイルの中の行なのか、表の中の行なのか。ここは「1 件ごと」にする。
かんたん層は最初から件数を「件」で数えており（Peak 47 件）、新しい抽象を持ち込んでいない。

**そのファイルについての事実**は「行」のまま残す。「47 行すべてが 1 件にまとまります」
「表の前にあった 23 行」は、いま画面に出ているファイルを説明していて、尺度のラベルではない。
`workbench:`（詳細モード）の語彙も残す — RML を読む人にとって行は正確。

| | 変える | 残す |
|---|---|---|
| ③ の帯 | ② 行ごとの値 → **1 件ごとの値** | — |
| ④ の図の箱 | 行ごと → **1 件ごと** | {列名} ごと |
| ④ の zone 表 | 行ごとに変わります → **1 件ごとに変わります**（かんたん専用の `zone.varies` を新設） | — |
| 種類の呼び方 | 行ごとの種類 → **1 件ごとの種類**（RML 用語ではなくただの日本語なので両層で統一） | — |
| 実データの説明 | — | 47 **行**すべてが / 表の前にあった 23 **行** |

**採らなかった案:「各値」。** ①も「値」なので、「各値」だと**何ごとに各なのか**が言えず、
対比の軸（どの単位で 1 件か）が消える。

### 数え上げの単位も直した
③の帯は列を数えているのに「{{count}} 件」と言っていた。このアプリで「件」はエンティティの
数（Peak 47 件）を指すので、同じ画面で 2 つの意味に使われていた。「{{count}} 列」にした
（かんたん層は表の見出しで既に「元の列名」と言っており、列は使ってよい言葉）。

### 描画エンジンを React Flow にした（かんたん層だけ・2026-08-29）

利用者:「マーメイド図より、Graphium のような cytoscape や reactflow のかっこいいグラフのほうが
楽しくなる」。実物（mermaid 版）を見たうえで試した結果、**かんたん層だけ**入れ替えた。

| | かんたん層（④⑤） | 詳細モード |
|---|---|---|
| 描画 | React Flow (`@xyflow/react`) | mermaid のまま |
| 図 | 触れる（拡大・移動・箱に触ると関係ない箱が引っ込む・押すと②の種類へ飛ぶ） | 幅いっぱいの静止画 |
| 理由 | 箱が増えるのも線が引かれるのもこの画面の**操作の結果**。静止画だと、変わったのが自分のせいか分からない | 読む人が違う。RML を読む人には静止画で足りる |

**形のデータ（`shapeGraph.ts`）と描画（`ShapeGraph.tsx`）を分けた。** ④は骨格から、⑤は取り込み
ルールから組むが、**絵の作り方は 1 つ**。別々に組むと「④で予告した形が⑤で実線になる」が
保証できない。並べかたも自前（React Flow は並べてくれない）＝入力順に決まる決定論で、同じ
設計は毎回同じ絵。

**⑤の箱は塗り分けない。** ④の色は「人がここで決めたこと」（ID にした値＝琥珀／ファイル全体の
カード＝緑）を表す。⑤に決めることは無く、取り込みルールからは 1 件のカードか行の種類かも
読めない（`crystal/{No}` の `No` は前置きの列）。**分からないことを塗り分けない**。

#### 実機で出た罠

- ⭐**`fitView` は初回しか効かない。** 箱が増えても拡大率が前のままで、図が横にはみ出す。
- ⭐**辺は箱の handle の実測（`handleBounds`）が取れるまで描かれない。** 図が後から差し込まれる
  画面（⑤は取り込みルールが届いてから現れる）では実測が空のまま固まり、**箱は出るのに矢印が
  1 本も出ない**。`ReactFlowProvider` の内側で `useUpdateNodeInternals()` と `fitView()` を
  形が変わるたびに明示的に呼ぶ。`key` で貼り替えるだけでは直らない。
- ⭐**同じ文言の辺ラベルは 1 度だけ。** 同じ親から 2 本出ると文字どうしが重なって両方読めない。
  予告（点線）はラベルを持たせない — 意味は図の下の注記が言っている。
- 細い列に 3 つ横並びにすると `fitView` が縮めて字が読めない。1 段 2 つで折り返す。
- `innerText` は「見えていない要素」で空を返す。実機の確認は `textContent` で。
