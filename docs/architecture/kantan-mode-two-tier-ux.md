# かんたん/詳細 二層モード — データセット追加 UX の再設計

status: 決定（ユーザー承認済 2026-07-21）→ 実装は段階的（先行条件 → UI 骨組み → 自動連結 → 試し検索）
関連: [`phase5-workbench-materialize-gate.md`](phase5-workbench-materialize-gate.md)（本 ADR が D1 を改訂）/ [`mapping-ir-phase2b-skeleton-wizard.md`](mapping-ir-phase2b-skeleton-wizard.md)（骨格ゲートを流用）/ [`ask-quality-and-generality.md`](ask-quality-and-generality.md)

## 0. 問題（開発者本人が「作った自分でも分からない」）

データセット追加フローが情報過多・専門用語過多で、オントロジーを知らない・IT リテラシーの低い実験科学者が初見で完走できない。12 エージェント分析（5 読解 → 3 設計案 → 3 視点審査 → 統合）による診断は 3 点:

1. **承認儀式**: 機械が既に守っているもの（422 ハードゲート `assert_rml_safe`/`validate_rml_design`・T1–T9 自動修正・draft 隔離・rollback）まで人間の承認ステップとして画面に並べており、承認文が「RML / Morph-KGC / Tier 0 / canonical」という実装名の弁明で埋まる（`workbench.json` `ingest.note` は 1 文に専門概念 6 語）。説明文は各機構が main に入るたびに「存在証明」として追記されたもので、「あなたは今どこにいて、あと何をすれば完了か」を語らない。
2. **進捗モデル不在**: 3 段ステッパーが「保存」で終点。取り込み・公開はカタログ側の別画面に分断され、promote 完了から Ask への直リンクも無い。実測: 初回公開まで能動的判断 20 回（Workbench）+12 回（カタログ）。
3. **入口の門前払い**: 最初の関門が LLM API キー入力（sk-… の概念ごと）。実験科学者の主データ形式 .xlsx を受理しない（`datasetsApi.ts` `TABULAR_ACCEPT`）。

## 1. 決定事項

| # | 論点 | 決定 | 理由 |
|---|---|---|---|
| K1 | 情報設計 | **二層モード**: 既定=「かんたんモード」（5 工程レシピカード常駐・9 画面）／「詳細モード」=現行 Workbench/カタログ全機能を**削除ゼロ**で温存。トグルで同一 dataset/job のまま往復 | 審査 3 視点（ペルソナ本人・品質の番人・UX リサーチャー）全員一致。初見者の完走と上級者の全能力を両立 |
| K2 | 人間ゲートの集約 | 人間の確認は **3 問だけ**: ① データの数えかた（=骨格ゲート）② 項目の意味（=設計レビュー）③ 公開（=promote）。いずれも「データの意味・公開意思」という**人間しか知り得ない事柄**を守る | 機械が保証できるもの（実行安全=422、引用面の純度=draft 隔離+promoted フラグ）を人間の承認から外し、残った 3 つだけを平易な質問形で前面化 |
| K3 | 保存→draft 取り込みの自動連結 | かんたん層では materialize 成功後に **draft への ingest を自動実行**（「確定して保存」「データを取り込む（承認）」の 2 ボタンを 1 工程に畳む）。**[`phase5-workbench-materialize-gate.md`](phase5-workbench-materialize-gate.md) D1（2 段ゲート）を改訂** | D1 制定時（#15）に承認ボタンが守っていたリスクは、その後の 422 ハードゲート（実行前検証）+ draft 隔離 + rollback finally 化 + 孤児 version graph 回収で**構造的に消えた**。未 promote データは誰にも見えず Ask も引用しない。詳細モードの明示ボタンは温存 |
| K4 | 用語ポリシー | かんたん層に fatal 級専門用語を**出さない**（RML・IRI・名前空間・canonical・draft graph・述語・クラス・トリプル・Morph-KGC・Tier 0…）。「グラフ」の語も使わない。同一概念の複数呼称（述語=プロパティ、設計図=語彙=スキーマ、共有データ=canonical=正式グラフ）は**層ごとに 1 本化**。**適用範囲の拡大（2026-07-23 決定）**: かんたんウィザードだけでなく**共有画面（ホーム/データセット/つながり/共通の言葉/引用カード等）にも同じ対訳を適用**する — かんたんで作った人が公開直後にカタログで旧用語に出会う断絶が実測されたため。専門表記の逃がし先は詳細ビューア（ルールタブの原文（RML 形式）・型列・高度な検索・詳細モード）に限定 | 「説明を読んでも分からない」の根因=説明の主語が信頼モデル（内部構造の弁明）。かんたん層の説明は常に「ユーザーの目的」を主語にする。共有画面は初見者も踏むため、かんたん側に 1 本化する |
| K5 | LLM 設定の撤去 | かんたん層から キー/モデル/base URL の概念を**全廃**。サーバ側キー（`/api/llm/server-keys`・実装済）を既定とし、未設定サーバのみ「管理者が AI の設定を済ませると使えます」1 枚（個人利用者にはファーストラン 1 画面） | 入口の門前払い解消。設定モーダルは詳細モードに温存 |
| K6 | .xlsx 受理 | .xlsx をサーバ側で表形式へ**決定論変換**して受理（変換ツール・版は来歴に記録）。多シート等で一意に決められない場合のみ「どのシートを使いますか？」の汎用質問にフォールバック | 実験科学者の主データ形式。docx/PDF→XML のサーバ側変換と同じ「vet 済み決定論アダプタ」パターン |
| K7 | 骨格ゲートの規律 | 全行一意でも**必ず 1 タップ確認**（auto-continue しない・[`mapping-ir-phase2b-skeleton-wizard.md`](mapping-ir-phase2b-skeleton-wizard.md) §9(b) 維持）。「重なったまま進む」を既定ボタンにしない。複数 map 時は緑の map を畳んでよいが、**畳んだ map にも「1 行=◯◯」の読み取り文を必ず表示**（意味誤り×偶然一意の素通り防止） | 品質の番人審査の最重要指摘。骨格ゲートは弱モデルが主キーを誤る実測があり（Phase 2b dogfood）、形骸化させない |
| K8 | 項目の意味の出所 | Mapping IR の property 行に **optional `label`（人間可読の意味）/ `unit`（単位）** を追加し、propose に書かせる。S6「項目の意味」テーブルと ontology projection の rdfs:label 補強がこれを消費。**散文（§1–8）からの投影代用は不可** | 現 IR に意味ラベルの置き場が無い（`mapping_ir_schema.py` 実測）。決定論投影の原則（AI を再度通さない）を守る |
| K9 | ためす（試し検索） | draft 取り込み直後に**決定論クエリ（件数・範囲・最大値+出典 IRI）を自動実行して見せる**。任意ボタンにしない（初見者は押さない）。生成できないデータ形は種類別件数+実 ID にフォールバック | 「引用できる事実」の価値をユーザー自身のデータで最初に体感させる。項目の意味の誤りをここでも発見できる |
| K10 | 公開経路の一本化 | 公開は確認ダイアログ（名前・種類別件数・ことばの要約・撤回可能性の約束）**一本**。未確定項目が 1 つでも残る限りボタン無効。カタログカード側のワンクリック公開は**初回公開では全モードでこのダイアログ必須** | 全自動案の審査で出た公開バイパスの穴を先に塞ぐ |
| K11 | 非収束時の出口 | 自動修正で解決できない場合のみ停止カード 1 枚。**全エラー系統→平易質問の翻訳テーブルを実装前に仕様化**（例: T2→「Excel で保存した CSV の文字化け対策をしています」）。出口は常に 2 つ: [AI にもう一度直させる][詳細モードで自分で直す] | 初見者の行き止まりを作らない。T1–T9 の生ラベルが「進行不能の主因」という用語棚卸しの実測に対応 |
| K12 | 件数の表現 | かんたん層はトリプル数を出さず**種類別件数**（「試料 24 件・測定 500 件」）。S6 に「元ファイル N 行 → …」の対応カードを常時表示 | 主キー潰れをユーザーが自分の目で発見できる（行数↔件数対応が最強の検証面） |
| K13 | 命名の決定論化（2026-07-23 追加） | mint 名前空間で**人間が判断する名前は「データセットの名前」（IRI 内 slug）1 つだけ**。CURIE prefix（略記）は slug から**機械導出**（`derive_prefix_pair`: 先頭トークン→衝突時トークン連結→`ds` 保険・resource は +`r`・NCName 安全）し、AI にも人間にも選ばせない。AI 提案骨格はサーバで**正規形に正規化**（`normalize_dataset_namespace`: `{base}/datasets/{slug}/ontology#`+`resource/` へ base/形ずれ・placeholder mint を修復、CURIE 連動 rename）。骨格ゲートは「データセットの名前」1 欄（rename cascade・編集は他のキー編集同様に再検査）+「ID の発行元」（base 未設定なら仮発行元警告+設定への案内。**base は設定の領分 — ゲートで編集させない**）。かんたん層は生 prefix 表を出さず（K4）、**ID テンプレート/クラス列/検査文言も mint 略記を縮約表示**（`measurement/{…}`・`Measurement` の相対形で表示・編集し、入力境界で mint prefix を機械付与。skeleton 状態は常にフル CURIE＝検査/continue は詳細層と同値。標準語彙 `schema:` はそのまま見せる）、詳細層は「高度」details に温存 | prefix は保存データに一切現れない純表記で、「何をつけたら良いか全くわからない」は正当な反応（2026-07-23 ZEM dogfood 実測）。意味を持つ判断（slug=将来この箱に何を足すか）だけを人間に残し、意味を持たない判断は機械が引き受ける — 修正レシピ（T1-T9）と同じ「機械的要件は機械が用意する」原則 |
| K14 | 骨格ゲートの帰結プレビュー（2026-08-13 追加） | ID の証拠を URL 構文でなく**帰結**で見せる: ①潰れ分類 `collapse_kind`（**全行→1 件の singleton は緑の正常系**「N 行が同じ 1 件に合流」・⚠ と続行 confirm は partial のみ）②**エンティティカード**（代表 1 件の実プロパティ値。partial は最大衝突グループの値の取り合いを実値+行番号で、singleton は行ごと列を「別の種類の領分」として列挙）③**参照リスク** `reference_risks`（measurement-id=値修正で引用が宙に浮く / scope-missing=singleton 親のキー列を含まず追記で混入）④scope-missing 時は候補チップを**親キー前置**（scoped）に書き換え、正解をワンクリック第 1 候補に。詳細は [`skeleton-gate-consequence-preview.md`](skeleton-gate-consequence-preview.md) | XRD 参照カード dogfood（2026-08-13）で開発者本人が「正解の潰れ」を事故と誤読し、正解キー `{No}/{(hkl)}` が候補に存在しなかった実測。人間が持つ知識は世界の側（1 材料・47 ピーク）で ID 構文ではない — K7 の証拠を人間の言葉に翻訳する |
| K15 | 適用範囲＝製品の全面（2026-08-18 追加） | K4 の用語ポリシーと K11 の「行き止まりを作らない」を**かんたんウィザードの外にも適用**する: 共有画面（ホーム／データセット／つながり／質問する／共通の言葉／アクティビティ）に加えて、**引用 ID の着地先（`/describe` と GitHub Pages の 404）・デスクトップ版の起動と停止・中断からの再開・英語ロケール**まで含む。専門表記の逃がし先は従来どおり詳細モードと `<details>`（「詳しい内容（技術情報）」「開発者向け」）に限定 | 16 面の網羅監査（2026-08-18）で、初見者が完走できなくなる blocker が**ウィザードの外**に集中していた（サーバ共有キーがあっても AI が使えない／引用リンクの着地先が英語で出口ゼロ／デスクトップが最大 60 秒無表示）。かんたんウィザードだけを平易にしても、その前後で人は詰まる |
| K16 | 人しか知らない訂正は AI を通さない（2026-08-18 追加） | **列の「意味」と「単位」の訂正は決定論のパッチで反映する**（`POST /api/datasets/{id}/display-meta` が §9 Mapping IR の当該 property の label/unit だけを splice → 6 artifacts を再投影）。LLM ラウンドも再取り込みも要らず、compiled RML はバイト不変（そうでなければ 409 で拒否）。人間が入れた値は控えを持ち、以後の refine ラウンドでも決定論で再主張する（N6）。自由記述欄は「設計そのもの（列の分け方・つながり）を変えたいとき」に限定する。同じ原則で、**公開時に S7 の決定論 3 問（種類別の件数・数値の範囲・最大の記録＋出どころ）をそのデータセットの typed query tool として登録**し、Ask の定型質問を弱いモデルの SPARQL 生成に依存させない | label/unit は IR 上「表示メタ」であり、機械が安全に書き換えられる。にもかかわらず訂正手段が「自由文＋LLM＋設計全体の作り直し」しか無く、弱いモデルは note を無視して別の場所を壊す実測があった（単位「K」を直したいだけの人がループする）。K13 と同じ「機械的要件は機械が用意する」の適用。**UI 側で質問文を文字列一致で横取りして回答カードを合成する案は不採用**（AI が答えていない文字列を AI の回答の形で出すことになり、「引用できる事実は決定論ツールが出す」という単一経路が崩れる） |
| K17 | 1 工程 = 1 画面（2026-08-19 追加） | レシピカードの工程は**画面と 1 対 1 にする**。旧「③ 確かめる」は S4（データの数えかた）と S6（項目の意味）という**別々の 2 画面**を 1 工程に畳んでおり、画面側は「確かめる（1/2）」「確かめる（2/2）」と番号で補っていた。これを **③ データの数えかた / ④ 項目の意味** に分け、画面見出しも工程名と同じ語にする（「確かめる（n/2）— 」を外す）。S5（自動処理）は機械の仕事なので工程名を持たず、向かう先である ④ を点灯させる | 実機レビューで「確かめるが 2 つある」「最後に『データの数えかたに戻る』ボタンがあるが、いま ためす と 確かめる のどちらにいるのか分からなくなった」と実測。戻り先ボタンは工程名を名指しするのに、その名前がカードのどの工程を指すのか対応が取れていなかった。そもそも ③④ は K2 が定める**人間の 3 ゲートのうちの 2 つ**であり、1 工程に畳むのは ADR 自身の人間ゲートの数え方とも食い違っていた |
| K18 | 工程名にソース形式の語を使わない（2026-08-20 追加） | レシピカードの工程名は、**その形式でしか通じない語（表の「行」「列」、文書の「段落」「節」）を使わない**。K17 で分けた 2 工程は **③ データの数えかた / ④ 項目の意味** とする（旧 ③ 行の数えかた / ④ 列の意味）。画面内の具体的な説明文は「1 行 = 1 つの試料の 1 回の測定」のように**そのソースの語のままでよい**（工程名だけを形式に依らない語にする）。④ の「項目」は §5 で述語/プロパティの対訳として既にあり、この画面はまさに項目に意味を与える場なので一致する。表の 1 列目「元の列名」は *ファイル側の名前* を指す別語のまま残す（衝突ではなく区別） | **画面内の「1 行 = ◯◯」も、まとまる設計では偽**（3,001 行 → 1 件の試料に対して「1 行 = 試料」）なので、**記録の数を言う文は「件」で言い切る**（骨格ゲートの表見出し・S6 のまとまり見出し）。ファイルの行を文字どおり指す文（「3,001 行すべてが 1 件にまとまります」）は行のまま — そこは実際に表の行の話であり、件にすると逆に嘘になる。 | 実機レビューで「この UI における行と列は、元のデータの行・列と一致しているか。一致していないとユーザーは何が行で何が列？となる」と実測。実際 ④ の画面は**「1 行 = …」と書きながら、その画面の表は 1 行が 1 つの『列』**を表しており、同じ語が 2 つの数え方を同時に指していた。さらに文書ソース（節→段落→文）では「行」「列」が存在せず、工程名が形式に依存していると**ソースを増やすたびに工程名が破綻する**。数えかた／項目という言い方は表・文書・装置ファイルのいずれでも成立する |

## 6. つながり（crosswalk）の対訳（2026-07-24 追加）

K4 の適用範囲を「つながり」画面へ拡大したときの正準。生の識別子（normalizer 名・
concept キー・視点 id）は**かんたん層に出さない** — 保存データに現れない純表記か、
機械が導出したものだからである（K13 と同じ原則）。専門表記の逃がし先は詳細層の
`<details>`（自分で組み合わせを決める）に限定する。

| 現行（専門語） | かんたん層 |
|---|---|
| crosswalk / 橋 / hub | つながり |
| perspective / 視点 | つながり（1 本＝1 つの「つなぎ方」） |
| 起点（source）/ 対象（target） | 左のつながり / 右のつながり |
| concept / 概念 | つなぐ手がかり |
| normalizer / 正規化（`nfkc` 等の id） | **文で言う**（「全角・半角や下付き数字のちがいは、同じものとして扱います。」） |
| shared value / 共有された値 | 両方に出てくる値 |
| participants / 参加データセット | つながっているデータ |
| build / rebuild | つくる / 最新のデータで作り直す |
| alignment / 整合 | 対応づけ |
| `equivalentClass` 同じ種類（≡） | 同じものを指す（記号は `title` に退避） |
| `subClassOf` 下位の種類（⊑） | 一部にあたる |
| discover / 候補検出 | つなげそうな組み合わせをさがす（**AI は使いません**と明記） |

**根拠となった実測（2026-07-24）**: 開発者本人がつながり画面で詰まった。原因は
① 作成導線が素のテキストのみ（しかも 1 本目ができると消える）② かんたんモードから
作成画面へ到達できない ③ 視点 0 件でも整合フォームが空の select を出し「ここで
データセットを選ぶ」と読まれる ④ データセット詳細の「外部の標準に合わせる」で
作った整合が同じ align API 経由で混入していた（「まだつながりがありません」と
言いながら整合行が出る矛盾）。

## K3 改訂（2026-08-18）— 欠陥の停止カードは機械が押す

**背景**: S5 の「AI に直してもらう」は `startRefineChain` を呼ぶだけ＝機械が実行できる動作そのもの。
人間は機械が持っていない情報を何も持たずに押しており、実測で 1 回の取り込みあたり 2〜5 回
押していた（2026-08-16〜18）。あの画面は判断の場ではなく、ただの摩擦だった。

**決定**: `kind: 'design'`（欠陥）の停止はウィザードが自分で修復を回す。カードは
「本当に判断が要るとき」だけ出す。

- 予算 3 ラウンド（サーバ側の自動ループ 5 と合わせて最大 8）
- **無進捗検出**: 同じ指摘集合が返ってきたら即座に人間へ。動かせなかったモデルは次も動かせない
- 進捗は `s5.fix.autoProgress`（「AI が自動で直しています（n/3 回目）」）として live 行に出す。
  カードは出さない
- **`kind: 'weakness'`（advisory）は従来どおり人間**。「この設計は薄すぎるか」は判断であって
  修復ではなく、単目的な設計は正当でありうる
- 手動ボタンは fallback として残す。人間が押したら無進捗メモリを消して予算を 1 つ戻す
  （人間が意図してラウンドを費やした＝そこから機械が続けてよい）

**判断ロジックは `ui/src/kantan/autoFix.ts` の純関数 `shouldAutoFix`**（ブラウザ無しで検証できる
形に切り出す。このリポジトリには UI テストランナーが無いため）。

### CSS の語彙（`.kz-` 名前空間・新しい色/余白トークンは作らない）

- **S4 の「証拠を 2 枚並び」は実装しない。** `SkeletonGate.tsx` の証拠はマップごとの
  `<tr>` として詳細モードと**同じ経路**で描かれており、横並びのグリッドにするには
  共有コンポーネントの描画構造そのものを変えることになる（案自身が「`plain` の分岐内
  だけを触ること」と釘を刺している範囲を超える）。3 種類以上のときの折り返し仕様も
  案に無い。読みやすさへの寄与は 4 項目のうち最も小さいと判断した。
- **S6 ①「数の確認」は数値を立てる**（2026-08-27 追加。当初この 1 点だけ実装から漏れて
  いた）。この区画で人が見るのは「行の数」と「件の数」が合っているかの 1 点なので、
  数だけを 1.3rem/700 で置き、ラベルと単位は添え物のまま小さくする。1 文
  （「元ファイル 20 行」）に埋めていたころは、比べたい 2 つの数が周りの文字と同じ
  大きさで、読むのではなく数えないと見つからなかった。
- **S6「AI の候補があれば意味欄を自動入力」は実装しない — データが存在しない。**
  `droppedColumns` は定義上「Mapping IR が使わなかった列」であり、要素は
  `{source, column, samples, maps}` だけで AI 由来の label を持たない（`ColumnDecision`
  にもフィールドが無い）。機械が出せる候補は元の列名だけなので、既存の
  「元の列名をそのまま使う」（行ごと＋一括）に文言を寄せた。
- **一括ボタンの閾値を 5 件超に上げない。** K22 の「2 行以上で表示」は 2026-08-25 に
  ユーザー要望（「一つ一つ『取り込む』を選ぶのは面倒」）で入ったばかりで、5 に上げると
  2〜5 列のときだけ 1 件ずつに逆戻りする。
- **S9 は 3 枚でなく最大 4 枚。** 案の 3 枚（標準のことば／人に見せる／育てかた）には
  「つながりを作る」が無く、そのまま実装すると 2 件目以降を公開した人から crosswalk の
  入口が消える。条件つきなので初回公開では案どおり 3 枚に見える。

### ついでに塞いだ穴（S4）

`reason == 'no-template'`（ID の作り方が空）は、潰れでも衝突でもないため `blockers` に
入っておらず、**そのまま「進む」が押せていた**。ここは K7 のソフトゲート（重なったまま
進む＝知った上での判断）とは別で、まだ形になっていない設計なので、`blockers` とは独立の
ハードな条件として締める（`continueAnyway` の迂回路に混ぜない）。同時に
`skeleton_annotate` がこの状態でも `key_candidates` を返すようにした — それまで候補が空で
「決められませんでした」とだけ言う行き止まりだった（K11）。

### 共有画面への適用（2026-08-26 追補）

K15 のとおり、K23 は公開したあとに人が居る面にも同じルールで通す。設計案が
「1 行 1 事実のカードに」「状態は色付きピルで先頭に」としか書いていなかった 3 面を、
実際の中身に合わせて具体化した記録:

- **つながり**は 3 つの事実の組（どのデータ同士が／どの値で／何を同じとみなして）
  なのに、参加チップの行・件数バッジ・同一視の 1 文が画面の別々の場所に散っていた。
  `XwLinkDiagram`（flexbox・SVG ではない）に集め、空状態・候補・詳細の 3 か所で
  同じ 1 枚を使う。空状態だけは実在のデータ名がまだ無いので総称で描く（在るように
  見せない）。3 つ以上つながる設計では横一列が崩れるので、ラベルを上に出して
  ノードを並べる形に落ちる。
- **候補カード**は `dt`/`dd` を縦積みにする。カードは grid のトラックの中に居るので
  ビューポート幅からはカード自身の幅が読めない（container query が要る形）。
  2 段組にすると狭いトラックで値の側が潰れ、関係図がデータ名の途中で折り返した。
- **共通の言葉**は語ごとに「標準のことば／このサーバだけ」を出す。まとめて質問
  しやすいかを決めるのはその語が外の世界と共有されているかどうかで、それが
  一覧の下の「再利用している語彙」表と読み合わせないと分からなかった。
- **引用カード**は見出しが人間の言葉、ID が副情報。label があるときは ID が
  どこにも出ておらず、「引用できる事実」の引用先そのものが画面から消えていた。

### 行長の決め方（2026-08-27 訂正）

当初は「列 880px」と「散文 62ch」を**両方**掛けていた。実データで見ると、`.kz-lead` は
1 行 34 字で折り返す一方、同じカードの表と対応カードは 55 字ぶんの幅いっぱいに広がるため、
段落の右に幅の 4 割ほどの空きが残り、**同じカードの中で左右の端が揃わない**。
利用者の言葉:「謎の右側の余白」。

**読み幅は列だけで決める。** 880px の列は 0.95rem で 1 行およそ 54 字＝日本語の推奨
（35〜45 字）の上限寄りだが、**すべてのブロックが同じ左右の端を共有する**ほうが、
1 つの段落だけが理想的な行長を持つことより読みやすい。`.kz-prose` は幅を足さず、
「散文である」という目印と `min-width: 0`（flex の子が列より広がらない保証）だけを持つ。

### S4 も採用デザインの形にする（2026-08-27）

当初 S4（データの数えかた）だけは表のまま残した — 証拠が詳細モードと同じ `<tr>` 経路で
描かれていて、横並びのグリッドにすると共有コンポーネントの描画構造そのものを変える
ことになるからだった。結果、**採用デザインを適用した他の画面との間で見え方が揃わず**、
利用者から「デザインを不採用にしたことで UX の不整合が起きている」と指摘された
（2026-08-27）。

**器だけを分ける**形で解決した: 1 種類ぶんの中身（「これは何か」「ID はどう決まるか」
「その証拠」）を **1 度だけ**組み立て、かんたん層はカード、詳細モードはこれまでどおりの
表の行として置く。同じ式を 2 か所に書かないので、片方を直すと両方に効く。詳細モードの
表の中身は 1 文字も変わらない。

**カードの中の幅は container query で組み替える。** カードの幅を決めるのは grid の
トラックであってビューポートではないので、media query では届かない（2 枚並びのとき
1 枚は 410px ほどになり、実物カードの 2 列の表では値の側が 250px に潰れて ⚠ の 1 文が
4 行に折れる）。`.skeleton-kind-card { container-type: inline-size }` を置き、
狭いカードでは実物カードの「項目名 / 値」を縦に積む。

あわせて:
- **「この種類は要らない」→「削除」**。名前がまだ無い行では「この種類」が何を指すか
  読めない（title には「この種類を設計から削除する」を残す）。
- **名前が無いときに機械の内部名へ落ちない。** `m.name`（`dataset` など）を
  「1 つの『dataset』」と言いながら、同じ画面の「1 件が表すもの」は空欄で聞いていた。
  人が書いていない語を答えとして見せない（K20）。名前が無いなら、無いと言う。
- **骨格の contract が種類名を必須にする**（`skeleton_json_schema` の subject に
  `classes: minItems 1`）。名前を付けるのがいちばん安いのは、列がまだ目の前にある
  骨格の段。完成した IR 側は据え置き（あとから足した規則で保存済みの設計を読めなくしない）。
- **行長の残り**: `.job-progress` / `.job-cancelled-note`（32rem）と
  `.skeleton-entity-card-box`（34rem）も列いっぱいに開いた。880px の列の中でこれらだけが
  512/544px になり、右に説明のつかない空きが出ていた。

### S4 の続き（2026-08-27・実機レビュー 2 巡目）

- **「1 件が表すもの」が空で返るのは、モデルの賢さの問題ではない。** `classes` を
  必須にした JSON schema は `response_schema` を持つ provider にしか届かず
  （`AnthropicLLMClient` にはこの属性が無いので、既定の Claude では schema が
  一度も送られない）、送れても `_load_json_object` は schema 検証をしない。
  三重にする: ①schema（届く provider には効く）②**抜けを名指ししたリトライ**
  （名前を付けるのに一番良い位置に居るのはモデル）③**決定論の床**
  `name_unnamed_kinds`（モデル自身の map 名から `peak` → `Peak`。何も無いところから
  発明した名前ではないので K20 に触れない。編集できる欄に ⚠ 付きで出るので、
  これは提案であって決定ではない）。
- **⚠ は入力欄の下。** 上に出していたころは、入力する前から「まだ決まっていません」が
  欄より先に目に入り、これから答える場所ではなく、すでに間違えた場所に見えていた。
- **削除はカードの右上にアイコンで。** 文字で本文の流れの中に置くと、読み終えるたびに
  目に入る。`aria-label` は「この種類を設計から削除する」（「削除」の 2 文字だけでは、
  名前がまだ無いカードで何を消すのか読めない）。
- **済んだ種類は畳む。タブにはしない。** 種類が増えたときに一覧性を壊すのは
  「並べ方」ではなく「開いている枚数」なので、答えの要らないものを 1 行に縮める。
  タブは①⚠ をタブの裏に隠せてしまう（見ないまま「進む」が押せる）②S4 の用は
  「試料 5 件 / 測定 20 件」を**見比べて**確かめることなので、1 つずつしか見えないと
  用が果たせない — どちらも K7 の趣旨に反する。K7 は既に「複数 map 時は緑の map を
  畳んでよいが、畳んだ map にも『1 行=◯◯』の読み取り文を必ず表示」と定めており、
  この実装はその指示そのもの。開いたままにするのは、名前が無い/検査できなかった/
  潰れている/直前に足した種類。

### 一覧性の本当の所在（2026-08-27・タブ案への回答）

利用者から 2 点の反論があり、どちらも私（実装側）の言い分より強かった:
①「タブに ⚠ を出せば見落とさないのでは」→ **そのとおり**。前節の「タブは警告を
隠す」は成り立たない（バッジを置けば済む）。②「2 個以上になったら、どちらの
並べ方でも見比べにくいのでは」→ **これもそのとおり**で、しかもここが本題だった。

**見比べる材料が、どこにも出ていなかった。** この画面で人が確かめるのは「元の
行数」と「種類ごとの件数」が意図と合っているかの 1 点なのに、その数は各カードの
証拠の奥（「この ID でできるもの: … 5 件」）にしか無い。カードを横に並べても、
タブで切り替えても、この確認はできない。

→ **S6 ①「数の確認」と同じ帯を S4 にも出す**（`元ファイル 20 行 → Sample 5 件
Measurement 20 件`）。これで**見比べは並べ方から切り離された**。カードを畳もうが
タブにしようが、この 1 行は常に見えている。

**カードが長い本当の原因も並べ方ではなかった。** 実物カードは食い違う列ごとに
同じ 1 文（「行によって値が食い違います — 同じ 1 件に、違う値が両方くっつきます」）
を繰り返しており、測定値の列が 3 つ食い違えば同じ文が 3 回出てカードの高さの
半分近くを占めていた。G9 の「常時見せるのは判断 1 行」に反する。→ **1 回言って、
列は ⚠ 付きの名前と値だけ並べる。**

この 2 つを直したうえで、タブと畳みの差は好みの範囲に縮んだ。**利用者の選択は
タブ**（2026-08-27）。タブ自身が ⚠ / ✓ を持つので警告は裏に隠れず、既定で開くのは
「まだ答えを待っている最初の種類」＝開いた瞬間にやることのある場所に居る。
パネルが列いっぱいを使えるので、実物カードの「項目名 / 値」も横 2 列のまま読める
（container query の縦積みは、狭いトラックが無くなったので発動しない）。

**同じ種類を二度書いた骨格を、骨格の段で止める。** 実データ（XRD reference file・
2026-08-27）で 1 ファイルに 5 種類が立ち、うち `Dataset` と `Sample` は**同じ列
`{No}` を鍵にして、どちらも表全体を 1 件に潰していた** — 読み取り文も件数も実物の
値も同じで、違うのは IRI の区間だけ。それぞれ単体では妥当なので誰も捕まえない。
`twin_maps`（source + iterator + 鍵の列の集合 + constant か）で見つけ、`classes`
の抜けと同じリトライに載せてモデルへ戻す。**機械が勝手に統合はしない** — どちらを
残すか（そもそも「両方、ただし列を分けて」が正解か）は設計の判断で、K2 は数えかたを
人の側に置いている。

### 「何を種類にするか」を教える（2026-08-27・利用者相談から）

利用者の問い:「reference という ID も出てきたが、他の論文データと crosswalk する
ことを想定して作っておくべきものなのか。どれだけ用意すべきか分かっていない」。

**事実の確認から**: つながり（crosswalk）は **ID ではなく値で結ぶ**
（[`crosswalk-hub.md`](crosswalk-hub.md): 参加データの正規化済みの値を集め、2 つ以上に
出てくる値ごとにハブの 1 件を作る）。**つながりのために種類を作る必要はない。**
種類にして得られるのは別のもの — ①引用できる住所（`/describe`）②「◯◯は何件？」に
答えられる ③同じ値が複数行・複数ファイルで **1 件にまとまる** ④それ自身に属性を
足せる。

**そして、直せる／直せないの線が判断を決める。** 意味・単位は後から決定論で直せる
（K16）。種類を増やすのも公開前なら自由。**ID の材料だけは公開したら直せない** —
IRI は引用の住所そのもので、変えれば渡したリンクが壊れる（K21 と同じ理由）。
**公開前に決め切るべきは「種類の数」ではなく「ID の材料」。**

実測された穴（XRD reference file・2026-08-27）:
1. **S4 の説明が手順しか言っていなかった。** 「⚠ が出たらこう直す」ばかりで、
   この画面で人が決める **何を種類にすべきか**を一言も言っていない。
   → 常時見せる 1 文を「外の世界も名前を持っているもの（組成・物質名・カタログ
   番号）は種類に、この表の中だけの値は項目のままで足りる」に書き換え、手順は畳む。
2. **AI が `Chemical Formula` を種類の候補に出したことがない。** 骨格プロンプトに
   「繰り返す・外とつながる値は種類に」という指針が無かった（`ENTITY LINKING` は
   鍵の設計の話で、昇格の話ではない）。→ `PROMOTE THE THINGS THE OUTSIDE WORLD
   ALSO NAMES` を追加。
3. **「AI にもう一度考えさせる」が S4 の編集を捨てる。** `onRethink` は
   `setSkeleton(null)` して S3 から作り直すので、種類名・ID・削除・切り出しは残らない
   （S6 の判断はデータセットに保存されているので残る）。**押す前に言う**ようにした。
   編集を保ったまま注文する形（現在の骨格を渡して差分で直させる）は未実装。
4. **「列を選んで種類に分ける」導線は既にあるのに、見出しが「ファイルを足したときの
   見え方」で、そこで種類を作れるとは読めなかった。** ボタン自身の文言
   （`splitLead`）は正しいのに辿り着けない。→ 見出しを「この中に別の『もの』が
   混じっていませんか？（列を選んで種類に分けられます）」に。

### 差し戻しは足すため。削るために使わない（2026-08-27・実測の後退）

前節で入れた「同じ鍵の重複をモデルへ差し戻す」は**取り消した**。実測（さくらの AI
Engine・XRD reference file）で「maps A, B … keep one」と伝えたところ、モデルは
**重複した 3 つのまとまりを全部落として map を 1 つにし**、前置きの 14 列が 47 行
すべてに写った。種類は 1 つしか出なくなった。

- **重複は差し戻さない。** どちらを残すか（そもそも「両方、ただし列を分けて」が
  正解か）は設計の判断で、K2 は数えかたを人の側に置いている。画面に出して人が
  🗑 で消す（`twinKinds`。該当する種類は「要確認」扱いなのでタブに ⚠ が付く）。
- **差し戻しは足すためのもの。** 名前の抜けだけを差し戻し、文面にも「いまある map は
  全部残して、足りない名前だけを足して」と書く。さらに**返ってきた答えが前より種類を
  減らしていたら、前の答えを採る**（`_generate_skeleton_gated` の no-shrink guard）。
  頼んだこと以上をやった答えは、進歩ではない。

一般則として: **LLM への差し戻しは「不足を埋める」ためだけに使う。「多すぎるものを
減らす」判断は決定論か人間に渡す。** 減らす指示は、どこまで減らすかの上限を持たない。

### 1 枚であることは「面」で言う（2026-08-27）

S4 だけで、外枠・タブの下線・種類カードの枠・証拠の縦線・実物カードの枠と、**5 本の
線が入れ子**になっていた。線が重なると、どれが「1 枚の境目」なのか読めない（利用者
評価「線が多すぎてカード感がない」）。

は `--surface` の白にするので、地と図で分かれる。同時に、カードが面になったことで
仕事を終えた線を落とす: タブの下線（選択中のタブは面で分かる）・証拠の縦線・成長
フォールドの破線。残る線は「外のカード 1 本」と「実物カード 1 本」の 2 本。

**分野に寄せた例示をしない**（同日）。「組成・物質名・カタログ番号のように」は材料系に
しか通じない。利用者向けの文は **「別のファイルや外のデータにも同じ値が出てくるもの」**
だけで足りる。モデル向けのプロンプトは例示が要る（指示が抽象的だと従えない）ので、

### K25 ID の区切りは `/` に正規化する（2026-08-27）

複合キーで LLM が `xr:peak/{No}_{2theta}` のように **区切り文字で 1 つの区間に融合**した
テンプレートを書くことがある。これは住所として危うい: 値そのものが `_` や `-` を含む
とき（`03-065-2664` のような登録番号は普通にある）、**別々の行が同じ IRI を作りうる**。
一意性の検査は「列の組」を見ていて、出来上がる文字列は見ていないので、検査は通る。

`normalize_key_separators`（決定論・`}…{` → `}/{`）を骨格の後段に置く。`_` は AI が
書いたもので、機械の規約は `/`。**人に見せる前に機械が直す**（C7-C11 と同じ筋）。

### K28 公開が済んだら下書きを消す（2026-08-27）

### K29 「まだ分からない」と「無い」は別のこと（2026-08-27）

利用者「関係性がつながってなくて良い？」— 見取り図に線が 1 本も無い画面を見ての

`object_template` として**次の段（項目の意味）で決まる**。見取り図の線は

ヘッダ部の定数どうし（登録番号・出典）はキーを共有しないので線にならない。

線が 0 本のとき（種類が 2 つ以上あるとき）、そう書く:
**「この段階では、線は ID の形から推測できるぶんだけです。種類どうしの本当の
つながりは、次の『項目の意味』で決まります。」**

つながらないまま公開へ進んだ場合は `_connectivity_advisories`（ingest 側・
グラフ形状だけを見る）が島を検出する。**この画面の役目は警告ではなく、
「ここで分かることの範囲」を言うこと。**

### K31 見取り図はかんたん層から降ろす（2026-08-27）

### K32 種類の選別はタブの前 — AI は推薦、決定は人（2026-08-27）

利用者「『別のものが混じっていませんか？』という流れでの種類の追加は変な体験。
すでに上にタブが出ているので、その段階で選別されていること自体が違和感。
あくまでもおすすめとして AI が出すだけで、最初の段階から選別を人間にさせては」。

**そのとおりで、G16 までの実装は「AI が選び終えた結果（タブ）＋修理の導線
（カードの中のチェック）」という形だった。** 「混じっていませんか？」という
見出しは昇格を異物検査のように言っており、選別は済んだことという前提を
画面が背負っていた。K2（数えかたは人の側に置く）に照らせば逆さまである。

作り直し: **タブの前に「この表全体の情報（この表で 1 件）」ゾーン**を置く。

| 行 | チェック | 右端のタグ |
|---|---|---|
| ヘッダ表の全列（値つき・省略なし） | **チェック＝この列をひとつの種類として数える** | — |
| AI が骨格で昇格した列（例: Reference） | **最初から ON**（＝AI のおすすめ） | 種類「xr:Reference」の ID |
| 表そのもののキー（例: CSD） | ON・固定 | この表の ID（xr:Crystal） |
| 行ごとに変わる列 | チェック無し（ゴースト行） | ↓「xr:Peak」の領分 |

- ON: 控えがあれば**元通り復元**（AI の名前・クラスごと）。無ければ G15 の
  split と同じ経路でその列をキーに 1 種類を作る。
- OFF: 種類を外す（控えに取ってから）。**可逆なので確認は挟まない** — 🗑 と
  違い、チェックし直せばそのまま戻る（G10 の可逆原則）。
- タブは「えらんだ種類をたしかめる」に格下げ。singleton のカードは同じ表を
  繰り返さず、ゾーンへの一文のポインタになる（G16 の「一覧は 1 つ」を維持）。

複数列で 1 つの概念（Name+Formula を 1 つの Substance に）は詳細モードの
split UI に残る。かんたん層は「1 列＝1 種類」で始め、まとめ直しは設計者の仕事。

実機（利用者の実 XRD ファイル）で 3 挙動を確認: ①Chemical Formula を ON →
件数バンドとタブに xr:ChemicalFormula 1 件が現れる ②Reference OFF → 消える
③再 ON → 控えから **xr:Reference** の名前のまま戻る。

### K33 種類にできる境界は「列の位置」でなく「値の性質」（2026-08-27）

利用者「『別のファイルにも同じ値が出てくるものは種類にしておくと…』と書いておいて、
(hkl) は選べないのは『なぜ hkl はできないの』とならないか」。**なる。** K32 の
ゾーンは基準を値の性質で述べながら、チェックはヘッダ列（＝ファイル定数）にしか
出していなかった。この境界はファイル形式の偶然で、1 試料 1 行の CSV なら組成は
「行側の列」になる — 位置で切る限り、形式が変わるたびに約束が破れる。

境界を「識別子か、測定値か」に引き直す:

- **識別子型の行列**（(hkl) のような名前・コード）→ ゴースト行にもチェックを出す。
  実サンプル（`(0,0,2)、(1,0,1)…`）を添える — 判断材料は値（G16 と同じ）。
- **測定値の列**（2theta / d / I）→ 出さない。測定値を ID にするのは K7 の罠で、
  こちらは**原理で説明できる境界**。

チェックすると **値のカタログ（value catalog）** ができる: `owns == キー列` の map。
その ID は値そのもの＝**同じ値の行が 1 件にまとまるのは意図**。この宣言で機械の
扱いが 3 か所変わる（どれも「事故」の機構がカタログを壊すのを防ぐ）:

| 機構 | カタログでの扱い | 放置した場合の誤爆 |
|---|---|---|
| ID 重複検査 | 「{{n}} 種類の値 → {{n}} 件」の肯定文・⚠なし | 意図した合流を事故として警告 |
| scope 自動修正（C7-C11） | **かけない** | `hkl/{No}/{(hkl)}` に書き換え＝ファイルを跨いで合流できなくなる |
| 行の置き場検出（G8） | 行の置き場に**数えない** | カタログがあるだけで missing_row_kind が黙る |

**リンクも生成任せにしない**: 所有された列の平文コピーは G6 が落とすので、
「リンクとして使え」だけでは弱いモデルで辺が消える。所有者の subject がその列
1 つで立つとき、`_generate_map_properties_gated` が落とした直後に決定論で
`{ontology}:{owner}` の辺を足す（label も決定論＝owner 名。付けないとこの機械の
辺 1 本のために label-fill の LLM ラウンドが走る）。

なお crosswalk は値そのもので照合するので、カタログにしなくても**照合**はできる。
カタログにする価値は「その値自身に引用できる ID を与える」こと — 選ぶのは人。

### K34 画面の名前は「そこで人がすること」を言う（2026-08-28）

利用者「もはや『データの数えかた』でフェーズは合っているのか。『1 行が何を表すか』
で合っているのか。『行』でよいのか。『もの』は entity の直訳では。全体的に自然な
日本語ではない」。

**全部当たっている。** S4 は K32/K33 で「種類を選ぶ場所」に変わったのに、名前と
リード文は旧設計（collapse の確認＝数えかた）のまま残っていた。文言は設計の変遷を
そのまま地層として溜め、誰も新鮮な目で読み直していなかった。

| 前 | 後 | 理由 |
|---|---|---|
| データの**数えかた** | データの**分けかた** | 画面の仕事は「ファイルをどんな種類に分けるか」。数（件数バンド）はその**帰結の証拠**であって、行為ではない |
| リード「『1 行が何を表すか』と、その行たちが共有する『もの』を決める画面です。…」 | 「このファイルを、どんな種類の記録に分けるかを決める画面です。分けかたの案は AI が作りました。種類ごとの名前と、1 件 1 件を見分ける ID を確かめて、違っていれば直してください。」 | 抽象の引用句で始めない。「もの」（entity の直訳）を使わない。3 文・各文 1 仕事 |
| ゾーン見出し「この表全体の情報（この表で 1 件）」 | 「**種類にする列をえらぶ**」 | K33 で行側の列も選べるようになり「表全体の情報」は不正確に。見出しは中身の説明でなく**行為**を言う |
| 「この数えかたで進む」 | 「この分けかたで進む」 | 名前に追従 |
| 「…もう一度考え**させられます**」 | 「…もう一度考えさせることができます」 | 使役可能と迷惑受け身が同形で誤読する |

原則として記録する:

- **画面名は行為（または行為の対象）で付ける。**結果の性質（数えかた）で付けると、
  画面が育ったとき名前だけ取り残される。
- **「もの」「対象」「要素」など entity/item の直訳語を利用者向けの文に使わない。**
  言い換え: 種類・記録・値・列・1 件。
- **「行」は文字どおり表の行を指す場所にだけ使う**（件数バンド・証拠文）。画面の
  定義文に「1 行が何を表すか」を使うのはやめる — いまの S4 の問いはもっと広い。
- 名前の変更は**参照ごと**（S6 の戻るボタン・再開の案内・空データの案内・stop card
  の選択肢・gateHow）。en も同時に（How the data is divided）。

### K35 目的から書く — S4 は「ID のつけかた」（2026-08-28）

利用者評価: ①「分けかた」は「なぜ分けるのか」の答えになっていない ②「種類」も
ピンと来ない ③自分の理解では**目的は別のファイル・別のデータとの橋渡し**で、
「crosswalk がつなげる場所なら、ここはつなげるための手を作る場所」。その理解で
合っているなら、ユーザーが「なるほど、じゃあこれは必要」となれる書き方にしてほしい。

**その理解は製品の設計そのものと一致している**（crosswalk-hub: 値の重なりが橋）。
だから画面の名前と文を、構造（分ける）ではなく**目的（つなぐ・引用する）**から書く:

| 場所 | 文 |
|---|---|
| フェーズ名 | **ID のつけかた** — この画面の全部（ゾーンの選択・タブの ID 検査・件数）が「どの値に ID を付け、どう作るか」で束ねられる。ID は引用と接続の正体 |
| リード | 「この画面では、どの値に ID を付けるかを決めます。ID の付いた値は、あとで別のファイルや外のデータと『同じ 1 件』としてつながり、引用にも使えます。…」 |
| ゾーン見出し | **あとでつなぐ値をえらぶ** |
| ゾーンのリード | 「…別のファイルや外のデータに同じ値が出てきたとき、**この 1 件が橋渡しの受け口になります**」 |

### 「もう一度考えさせる」は作り直しではなく修理（2026-08-27）
前節の実測 3 で残した宿題（「編集を保ったまま注文する形は未実装」）の答え。
**問題**: S4 の「AI にもう一度考えさせる」は `setSkeleton(null)` して S3 から
作り直していた。S4 でやった編集 — 種類の名前・ID の作り方・種類の削除・列の切り出し
— は保存先が無いので全部消えた（S6 の判断はデータセットに保存されていて materialize
で再適用されるので残る）。注文は「この 1 か所を直して」なのに、代金は毎回「全部」で、
押す前に ⚠ で「消えます」と断るしかなかった。
**決定**: 画面にある骨格をプロンプトに渡し、**注文の箇所だけ直させる**。
削除も切り出しも、渡す骨格に既に入っているので、渡した時点で反映済みになる。
| 層 | 何をするか |
| 文面（`render_rethink_request`） | 骨格そのものを JSON で渡し、「**Keep EVERY map above**・注文が触れていない map はそのまま返せ・種類を消す/まとめるのは人の判断」と書く。減らせとは**言わない**（前節の一般則） |
| 差し戻しの床（`_generate_skeleton_gated`） | no-shrink guard の比較相手を「前のラウンドの答え」から**いま画面にある骨格**に変える。答えが読めなかったときの持ち帰り先も、決定論の初期骨格ではなく**その骨格**（注文が通らないことと、編集が消えることは別の損失） |
| 人の値の控え（`human_pinned_edits`） | AI が最後に返した骨格（`aiSkeleton`）と画面の骨格の**差**が、人が打った値。ゲートはその 2 つの間にある唯一のもの。控えが無い（古いセッション）なら「人の値だ」と主張しない — 証明できないほうに倒す |
| 再主張（`reassert_human_edits`） | 返答が人の種類名・ID を書き戻していたら戻す。人が触った種類が答えから消えていたら戻す。**触っていない種類はモデルに任せる**（それが注文の中身）。直したことは `kept_human_edits` として画面に出す |
| 名前空間 | mint prefix は rethink で変わる理由が無い（K13＝機械導出）。slug が変われば全 ID が別物になるので、画面の値を先に置いて勝たせる |
| 機械の鍵差し替え | `apply_key_safety_fix(keep=…)`。「判断は残っていない」という前提は、**誰も判断していない間だけ**成り立つ。人が打った ID の map は対象外 |
**なぜ文面と決定論の両方が要るか**: 決定論だけだと、モデルは毎回同じ上書きを返して
きて、機械が毎回それを直す。文面だけだと守られない。`owned_elsewhere` +
`drop_borrowed_properties` と同じ対（頼む側と保証する側）。
**画面**: `skeletongate:rethinkResets`（⚠「消えます」）は `rethinkKeeps`（「残ります」）
に置き換えた。加えて S3 の再試行は**同じ注文で**再送し、途中で止めた/失敗したときの
戻り先は S2 ではなく S4（直そうとしていた設計はまだ手元にある）。
**残る非対称**: 「ID を変えて」と自然文で注文しつつ、その ID を自分で打ってもいた
場合、人の直接編集が勝つ（注文は効かない）。手で書いた ID を AI が書き換える事故の
ほうが高くつき、人はその場でもう一度手で直せる。

### K45 ゾーンは「ヘッダ付きファイル」だけの機能になっていた（2026-08-28）

利用者が**別のデータ**（元素表・119 行の普通の CSV）で試したところ、
**①「あとでつなぐ値をえらぶ」が丸ごと出なかった**。

原因: ゾーンの宿主を `collapse_kind === 'singleton'`（＝1 ファイルに 1 件のカード）
に限っていた。XRD 参考カードのような**ヘッダ付きファイル**にはこれが必ずあるが、
普通の行データには存在しない。K32 を XRD の形だけを見て書いたための穴で、
**列がいちばん多い普通のファイルでこそ、どの値をつなぐか決める場所が無かった。**

しかも実害は静かだった: AI は `PersonDiscovered` / `Category` などを勝手に昇格
させており、**人はそれを見ることも変えることもできなかった**（K32 の「AI は推薦、
決定は人」が、この形のファイルでは成立していなかった）。

直し:

- 宿主は「1 件のカード」が第一候補、無ければ**いちばん件数の多い行の種類**
- チェックを出す列は、singleton なら `growth_preview.described_columns`、
  行の種類なら**カード自身の識別子型の列**（新 `entity_preview.identity_columns`
  ＝キーでなく、測定値でもない列）

実機（元素表 20 行）: ①が出て `name / atomic_number / discovered_by[済] /
category / phase` が並ぶ。`symbol` はこの表の ID なのでチェック無し、
`atomic_mass` は測定値なので候補外。`category` を ON → `el:Category 7 件` が
即座に増え、`discovered_by` を OFF → `el:PersonDiscovered` が消える。

**教訓: 1 つの実データで設計した画面は、その実データの形に固有の前提を持つ。
形の違うデータで一度通すまで「仕様」と呼ばない。**

### K46 消し方は付け方と同じ操作にする（2026-08-28）

利用者「削除ボタンではなくチェックで消したいかも。**気軽にチェックつけれたのに
気軽に消せないのは辛い**」「チェックが付いているときと付いていないときがあるのは何？」

**チェックで消せる設計になっていた。消せない種類があったのは、その列がゾーンに
出ていなかったから。** カードの列は G13 の上限（8 列）で打ち切られており、ゾーンは
その打ち切られた一覧を並べていた。実データでは `Wikipage` / `BohrModelImage` /
`SpectralImage` が 8 列の外にあり、**🗑 でしか消せなかった**。

上限はタブ②のカード（読ませるもの）のためのもので、①は**一覧そのもの**。
`entity_preview.all_values`（全列＋代表行の値）を足し、①はこれを並べる。
`identity_columns` も打ち切らない。②のカードは従来どおり 8 列で切る。

**チェックの 3 つの状態**もリード文で言う（利用者が読み取れなかった＝書いていなかった）:

| 見た目 | 意味 |
|---|---|
| チェック済み | すでに種類になっている（**初期状態は AI のおすすめ**）。外すとその種類は消える |
| 空のチェック | 種類にできる候補 |
| チェック欄が無い | この表の ID に使われている／測定した数値（値が同じでも同じものを指さない） |

実機（15 列・4 種類）: ①に 15 列すべてが並び、8 列の外の `source[済]` /
`bohr_model_image[済]` も出る。`bohr_model_image` を外すと `el:BohrModelImage` の
タブが消え、もう一度チェックすると戻る。**🗑 に触らずに種類を出し入れできる。**
